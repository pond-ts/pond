# Performance

## Threads, without changing the answer

pond-rs uses several cores through the `parallel` Cargo feature, which is on
by default. Two kinds of work are split across threads:

- the **output columns** of one `rolling` or `aggregate` call, and
- the **partitions** of a `PartitionedSeries`.

Each column, and each partition, is still computed start to finish by one
thread, in order. That matters because adding the same numbers in a
different order can change the last digit of the result. Because pond-rs
never splits one column's rows between threads, the answer is the same, to
the bit, on 1 thread or 16. A test checks this on 1, 4 and 7 threads.

The thread pool is [rayon](https://docs.rs/rayon)'s. Set
`RAYON_NUM_THREADS` to choose its size. To build without threads:

```toml
pond-rs = { git = "https://github.com/pond-ts/pond", default-features = false }
```

The limit of this design: a call with a single output column, on a series
that is not partitioned, uses one core.

## What was measured

The numbers below come from the pond-rs plan
([`docs/plans/PND_RUST_PLAN.md`](https://github.com/pond-ts/pond/blob/main/docs/plans/PND_RUST_PLAN.md))
and can be re-run from `crates/pond-rs/bench/` and
`crates/pond-rs/examples/`. All were taken on the same 4-core machine.
Times are milliseconds of computing, not counting reading the file; lower is
better. Runs varied by roughly ±20%, so treat small differences as noise.

### Rolling windows and buckets on 1 million rows

**Workload A** is a general one: 1 million rows one second apart, four
number columns with about 5% gaps (and three 10-minute outages where
everything is missing). It runs per-minute buckets with average, minimum,
maximum and count, and a 5-minute rolling average and standard deviation.
**Workload B** buckets the same file by calendar day in New York; the data
crosses the 8 March 2026 clock change, so one day is 23 hours long. Each
cell is the range over three full runs, each run the median of seven.

| Workload | pond-ts   | pond-rs, 1 thread | pond-rs, 4 threads | polars, 1 thread | polars, 4 threads |
| -------- | --------- | ----------------- | ------------------ | ---------------- | ----------------- |
| A        | 2901–3412 | 438–504           | **141–159**        | 519–590          | 209–231           |
| B        | 77–115    | 31–47             | **11–14**          | 22–28            | 11–14             |

What this shows:

- On one core, pond-rs is about **6.5× faster than pond-ts** on A and about
  2.4× on B.
- On 4 cores, pond-rs is **faster than polars on A** and level with it on B.
- The one case where pond-rs loses: B on one core, where polars is faster
  (22–28 against 31–47 ms).
- Every pond-rs result here is identical, bit for bit, to pond-ts's.

Memory added during one run (MB, lower is better): on A, pond-rs 192,
polars on one thread 256, pond-ts 362 (which includes memory its garbage collector had not yet
freed); on B, pond-rs 78, polars 110.

### Per-entity work: 500 symbols

500 symbols × 1,000 one-minute bars (500,000 rows, symbols interleaved, 2%
gaps), run through `partition_by("symbol")` and then put back together.
Middle (median) time of several runs:

| Task                                              | pond-rs, 4 threads | pond-rs, 1 thread | pond-ts |
| ------------------------------------------------- | ------------------ | ----------------- | ------- |
| split into partitions                             | 17.5               | 29.0              | 28.7    |
| `diff`, then collect                              | 45.4               | 89.6              | 637     |
| `fill` (linear), then collect                     | 45.6               | 107               | 811     |
| rolling 60-minute mean, stdev, last, then collect | 67.7               | 143               | 992     |
| rolling, then the last value per symbol, top 20   | 36.4               | 84.5              | 1072    |

Most of pond-ts's time here goes into putting the partitions back together
(about 450 ms of it), which is logged as a pond-ts issue to fix.

### Agents writing code against it

pond-rs is built mainly for AI agents writing Rust, so one test was about
them. Twenty fresh agents were given the same task: daily average, minimum,
maximum and count by New York calendar day over the benchmark file. Ten used
pond-rs, ten used polars. None had web access; each could only read the
library's source.

|                                       | pond-rs | polars  |
| ------------------------------------- | ------- | ------- |
| right answer                          | 10 / 10 | 10 / 10 |
| right on the first run                | 9 / 10  | 6 / 10  |
| failed runs before the first good one | 2       | 4       |
| failed runs in total                  | 2       | 10      |

Both sides got every answer right, so this does not show that pond-rs makes
agents more correct, only that they needed fewer tries. Six of polars'
failed runs came after a right answer, while agents were adding their own
checks. What the pond-rs agents struggled with (no way to rename or drop
fields on output, and having to add the Arrow crate themselves) has since
been fixed with `select`, `rename`, `as_time` and the Arrow re-exports.

The trial's setup, task, grader and results are in
`crates/pond-rs/bench/agent-trial/`.
