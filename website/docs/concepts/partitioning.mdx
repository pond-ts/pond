# Partitioning

Real-world time series are usually **multi-entity** — events from
many hosts, regions, devices, or users interleaved in one stream by
time. Pond's stateful operators (`rolling`, `aggregate`, `fill`,
`diff`, `rate`, `smooth`, ...) read neighbouring events when
computing each output. On a multi-entity series, those "neighbours"
silently cross entity boundaries — the canonical pond footgun.

`partitionBy(col)` is the fix: split a series by column value,
operate per-partition, optionally fan back in.

## The cross-partition hazard

Take this series — two hosts interleaved by time:

```
time     | cpu  | host
0        | 0.5  | api-1
0        | 0.7  | api-2
60_000   | 0.6  | api-1
60_000   | 0.8  | api-2
```

Run a stateful op directly on it:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
series.rolling('5m', { cpu: 'avg' });
// → averages api-1 AND api-2 together. Probably not what you wanted.

series.fill({ cpu: 'linear' });
// → fills api-1's gaps using api-2's values as "neighbours."

series.diff('cpu');
// → diffs api-1's cpu against api-2's preceding cpu.
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::{Column, TimeSeries};

fn main() -> Result<(), pond_rs::PondError> {
    let s = TimeSeries::new(
        "cpu",
        vec![0, 0, 1_000, 1_000],
        vec![
            Column::required("host", vec!["api-1", "api-2", "api-1", "api-2"]),
            Column::required("cpu", vec![1.0, 10.0, 3.0, 40.0]),
        ],
    )?;
    // Each row minus the row directly above it, whichever host that was.
    let mixed = s.diff(&["cpu"])?;
    // Row 2 is api-1 minus api-2: a meaningless number.
    assert_eq!(mixed.column("cpu")?.numbers()?.get(2), Some(-7.0));
    Ok(())
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

s = pond.TimeSeries({
    "time": [0, 0, 1_000, 1_000],
    "host": ["api-1", "api-2", "api-1", "api-2"],

assert mixed.column("cpu")[2] == -7.0
```

</TabItem>
</Tabs>

Static (per-event) ops are fine — `filter`, `map`, `select`,
`rename`, `collapse` look at one event at a time. The hazard is
specifically with operators that read across multiple events:

- **Multi-event reads:** `rolling`, `aggregate`, `reduce`, `smooth`,
  `align`, `cumulative`
- **Adjacent-event reads:** `diff`, `rate`, `pctChange`, `shift`,
  `fill` (for `linear` and `bfill`)
- **Late-event reads (live):** `LiveRollingAggregation`,
  `LiveAggregation`, `LiveView.window`, plus the live versions of
  the above

## `partitionBy(col)` — per-entity scope

Split the series by column value, run ops within each entity,
materialise back:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
series
  .partitionBy('host')
  .fill({ cpu: 'linear' }) // per-host fill — no cross-host neighbours
  .rolling('5m', { cpu: 'avg' }) // per-host rolling — no cross-host averaging
  .collect(); // → regular TimeSeries, per-host outputs interleaved by time
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::{Agg, Column, Fill, Float64Column, Reducer, TimeSeries};

fn main() -> Result<(), pond_rs::PondError> {
    let s = TimeSeries::new(
        "cpu",
        vec![0, 0, 60_000, 60_000, 120_000, 120_000],
        vec![
            Column::required("host", vec!["api-1", "api-2", "api-1", "api-2", "api-1", "api-2"]),
            Column::optional(
                "cpu",
                Float64Column::from_options([Some(1.0), Some(10.0), None, Some(20.0), Some(3.0), Some(30.0)]),
            ),
        ],
    )?;
    let per_host = s
        .partition_by(&["host"])?
        .fill(&[("cpu", Fill::Linear)])? // per-host fill: no cross-host neighbours
        .rolling("5m", &[Agg::of("cpu", Reducer::Avg)])? // per-host rolling
        .collect()?; // a plain TimeSeries again, rows in time order
    // api-1's gap is filled from api-1's own readings (1 and 3), not api-2's.
    assert_eq!(per_host.len(), 6);
    assert_eq!(per_host.column("cpu")?.numbers()?.get(2), Some(1.5)); // avg(1, 2)
    Ok(())
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

s = pond.TimeSeries({
    "time": [0, 0, 60_000, 60_000, 120_000, 120_000],
    "host": ["api-1", "api-2", "api-1", "api-2", "api-1", "api-2"],
    "cpu": [1.0, 10.0, None, 20.0, 3.0, 30.0],
})
per_host = (
    s.partition_by("host")
    .fill({"cpu": "linear"})  # per-host fill: no cross-host neighbours
    .rolling("5m", {"cpu": "avg"})  # per-host rolling
    .collect()  # a plain TimeSeries again, rows in time order
)
# api-1's gap is filled from api-1's own readings (1 and 3), not api-2's.
assert len(per_host) == 6
assert per_host.column("cpu")[2] == 1.5  # avg(1, 2)
```

</TabItem>
</Tabs>

Each step in the chain returns a partitioned view
(`PartitionedTimeSeries` in TypeScript, `PartitionedSeries` in Rust and
Python) —
the per-partition scope persists across chains. `.collect()` is
what materialises back to a normal `TimeSeries`.

## Composite partitions

Multiple partition columns combine into a tuple key:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
series.partitionBy(['host', 'region']).rolling('5m', { cpu: 'avg' });
// each (host, region) combination gets its own rolling window
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::{Agg, Column, Reducer, TimeSeries};

fn main() -> Result<(), pond_rs::PondError> {
    let s = TimeSeries::new(
        "cpu",
        vec![0, 0, 0, 60_000],
        vec![
            Column::required("host", vec!["api-1", "api-1", "api-2", "api-1"]),
            Column::required("region", vec!["eu", "us", "eu", "eu"]),
            Column::required("cpu", vec![1.0, 5.0, 9.0, 3.0]),
        ],
    )?;
    // Each (host, region) pair gets its own rolling window.
    let out = s
        .partition_by(&["host", "region"])?
        .rolling("5m", &[Agg::of("cpu", Reducer::Avg)])?
        .collect()?;
    assert_eq!(out.column("cpu")?.numbers()?.get(3), Some(2.0)); // (api-1, eu): avg(1, 3)
    Ok(())
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

s = pond.TimeSeries({
    "time": [0, 0, 0, 60_000],
    "host": ["api-1", "api-1", "api-2", "api-1"],
    "region": ["eu", "us", "eu", "eu"],
    "cpu": [1.0, 5.0, 9.0, 3.0],
})
# Each (host, region) pair gets its own rolling window.
out = s.partition_by(["host", "region"]).rolling("5m", {"cpu": "avg"}).collect()
assert out.column("cpu")[3] == 2.0  # (api-1, eu): avg(1, 3)
```

</TabItem>
</Tabs>

Order matters for output sorting (events within a partition stay
in time order; partitions are visited in column-tuple order at
collect time).

## Live partitioning

The same hazard exists on the live side, with the same fix.
`live.partitionBy(col)` returns a `LivePartitionedSeries` that
routes incoming events into per-partition `LiveSeries<S>`
sub-buffers:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const partitioned = live.partitionBy('host');

// Per-partition rolling — each host gets its own deque
const rolledByHost = partitioned.rolling('5m', { cpu: 'avg' });

// Materialise per-host current values into a Map
const byHost = partitioned.toMap();
byHost.get('api-1')?.last()?.get('cpu');
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, LiveView, PartitionOptions};
use pond_rs::{ColumnDef, ColumnKind};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "cpu",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("host", ColumnKind::String),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let hosts = live.partition_by(live.root(), "host", &PartitionOptions::new())?;

    live.push(0, [Some("api-1".into()), Some(0.25.into())])?;
    live.push(1_000, [Some("api-2".into()), Some(0.75.into())])?;
    live.push(2_000, [Some("api-1".into()), Some(0.5.into())])?;

    // Each host's own series, built when its first event arrived.
    assert_eq!(live[hosts].keys(), ["api-1", "api-2"]);
    let api_1 = live[hosts].partition("api-1").unwrap();
    assert_eq!(live[api_1].last().unwrap().number("cpu")?, Some(0.5));

    // Per-partition steps: a chain built on every host, now and later.
    let per_host = live.per_partition(hosts, |live, host| Ok(live.window(host, "5m")?.id()))?;
    let built = live.partition_outputs(per_host)?;
    let window = live.node::<LiveView>(built[0].1)?;
    assert_eq!(live[window].len(), 2);
    Ok(())
}
```

In Rust a partitioned node is read with `live[hosts]` (`keys()`, `partition("api-1")`), and `per_partition` describes a chain built on every host, including hosts that arrive later. See [Live series in Rust](/docs/rust/live).

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

live = pond.LiveSeries({"time": "time", "host": "string", "cpu": "number"}, name="cpu")
hosts = live.partition_by("host")

# Per-partition rolling: each host gets its own window.
rolled_by_host = hosts.rolling("5m", {"cpu": ("cpu", "avg"), "host": ("host", "last")}).collect()

live.push(0, host="api-1", cpu=0.25)
live.push(1_000, host="api-2", cpu=0.75)
live.push(2_000, host="api-1", cpu=0.5)

# Each host's own series, built when its first event arrived.
assert hosts.keys() == ["api-1", "api-2"]
assert hosts.partition("api-1").last()["cpu"] == 0.5
assert rolled_by_host.last()["cpu"] == 0.375  # api-1: avg(0.25, 0.5)
```

In Python steps built on the partitioned node run per host; `collect()` gathers them. A live partition's output does not carry the host column by itself, so add it through a reducer (`("host", "last")`), as here.

</TabItem>
</Tabs>

Live partitions are **auto-spawned**: the first time an event
with a new partition value arrives, a sub-buffer is allocated for
it. Pre-declare the expected set with
`partitionBy('host', { groups: [...] })` if you want unknown
values to throw at ingest.

Per-partition retention, grace, and ordering all default from the
source's settings but can be overridden:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
live.partitionBy('host', {
  retention: { maxEvents: 1_000 }, // per-partition cap
  graceWindow: '5s',
  ordering: 'reorder',
});
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, OrderingMode, PartitionOptions};
use pond_rs::{ColumnDef, ColumnKind};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "cpu",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("host", ColumnKind::String),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let hosts = live.partition_by(
        live.root(),
        "host",
        &PartitionOptions::new()
            .max_events(1_000) // per-partition cap
            .grace_window("5s")
            .ordering(OrderingMode::Reorder)
            .groups(&["api-1", "api-2"]), // any other host is refused
    )?;
    assert_eq!(live[hosts].keys(), ["api-1", "api-2"]);
    assert!(live.push(0, [Some("api-3".into()), Some(0.5.into())]).is_err());
    Ok(())
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

live = pond.LiveSeries({"time": "time", "host": "string", "cpu": "number"})
hosts = live.partition_by(
    "host",
    max_events=1_000,  # per-partition cap
    grace_window="5s",
    ordering="reorder",
```

## Synchronised partitioned rolling

Per-partition rolling fires when each partition's own events
arrive — `api-1` updates at `api-1`'s pace, `api-2` at `api-2`'s.
That's correct for "I want host-1's smoothed value as soon as
host-1 has new data."

Sometimes you want all partitions to emit _together_ at fixed
boundaries — every host reports its current rolling-window value
on the same 200ms tick. Pass a clock trigger:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const ticks = live
  .partitionBy('host')
  .rolling('1m', { cpu: 'avg' }, { trigger: Trigger.every('200ms') });

// ticks: LiveSource<{ time, host, cpu }>
// Each tick → one event per known partition, all sharing the same ts
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, PartitionOptions, RollingOptions, Trigger};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "cpu",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("host", ColumnKind::String),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let hosts = live.partition_by(live.root(), "host", &PartitionOptions::new())?;
    let ticks = live.partition_rolling(
        hosts,
        "1m",
        &[Agg::of("cpu", Reducer::Avg)],
        &RollingOptions::new().trigger(Trigger::every("200ms")?),
    )?;

    live.push(0, [Some("api-1".into()), Some(1.0.into())])?;
    live.push(50, [Some("api-2".into()), Some(3.0.into())])?;
    live.push(210, [Some("api-1".into()), Some(2.0.into())])?; // passes 200 ms

    // Each tick: one row per known host, all sharing the tick's time.
    let rows: Vec<(i64, String)> = live[ticks]
        .events()
        .map(|e| (e.begin(), e.string("host").unwrap().unwrap().to_string()))
        .collect();
    assert_eq!(rows, [(200, "api-1".to_string()), (200, "api-2".to_string())]);
    Ok(())
}
```

</TabItem>
<TabItem value="python" label="Python">

```python
import pond

live = pond.LiveSeries({"time": "time", "host": "string", "cpu": "number"})

live.push(0, host="api-1", cpu=1.0)

assert [(e.begin, e["host"]) for e in ticks.events()] == [(200, "api-1"), (200, "api-2")]
```

</TabItem>
</Tabs>

The output is a flat `LiveSource` whose schema is
`[time, <partitionColumn>, ...mappingColumns]`. One event per known
partition per tick. Quiet partitions still emit (using their last
known rolling-window state, with stale entries evicted against the
tick timestamp).

This is what dashboards reach for: every host emits a coherent
snapshot at a regular cadence so the renderer can group by `ts`
and lay out a row per host. See
[Triggers × partitioning](./triggers#trigger--partitioning).

When the dashboard wants **multiple windows per partition** (e.g.
1m baseline + 200ms current), pass the keyed-record form instead
of a single `(window, mapping)` pair — see
[Windowing → Multi-window rolling (live)](./windowing#multi-window-rolling-live).
One ingest pass updates all windows; one merged event per
partition per tick. The shared shape:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const fused = live.partitionBy('host').rolling(
  {
    '1m': {
      cpu_avg: { from: 'cpu', using: 'avg' },
      cpu_sd: { from: 'cpu', using: 'stdev' },
    },
    '200ms': { cpu_samples: { from: 'cpu', using: 'samples' } },
  },
  { trigger: Trigger.every('200ms') },
);
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, PartitionOptions, RollingOptions, RollingWindow, Trigger};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "cpu",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("host", ColumnKind::String),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let hosts = live.partition_by(live.root(), "host", &PartitionOptions::new())?;
    let fused = live.partition_rolling_windows(
        hosts,
        &[
            RollingWindow::new(
                "1m",
                &[Agg::new("cpu_avg", "cpu", Reducer::Avg), Agg::new("cpu_sd", "cpu", Reducer::Stdev)],
            ),
            RollingWindow::new("200ms", &[Agg::new("cpu_samples", "cpu", Reducer::Samples)]),
        ],
        &RollingOptions::new().trigger(Trigger::every("200ms")?),
    )?;
    let names: Vec<&str> = live[fused].schema().iter().map(|c| c.name.as_str()).collect();
    assert_eq!(names, ["time", "host", "cpu_avg", "cpu_sd", "cpu_samples"]);
    Ok(())
}
```

## Fan-in patterns

Three ways to consume per-partition output (the table uses the
TypeScript names; Rust and Python have `collect` and `apply` under the
same names, and read partitions with `partition(key)` / `partitions()`
rather than `toMap()`):

| Pattern              | Returns                                           | Use when                                       |
| -------------------- | ------------------------------------------------- | ---------------------------------------------- |
| `.collect()` (batch) | `TimeSeries<S>` with all partitions merged        | Batch chains — final materialise step          |
| `.collect()` (live)  | `LiveSeries<S>` (append-only fan-in)              | Live: unified rolling buffer per host's events |
| `.toMap()` (live)    | `Map<key, LiveSource<S>>`                         | Direct per-partition subscription              |
| `.apply(factory)`    | `LivePartitionedView<R>` of per-partition outputs | Chain a factory across all partitions          |

The synchronised-rolling output above bypasses fan-in — it returns
a flat `LiveSource` directly because the boundary-tick contract
already gives you one event per partition per tick.

## What partitioning doesn't do

- **Doesn't share state across partitions.** Each partition has
  its own rolling deque, its own bucket states, its own subscriber
  list. This is intentional — partitions are independent by
  construction, which is the whole point.
- **Doesn't auto-merge late events across partitions.** A late
  event for `api-1` does not perturb `api-2`'s state. Live
  partitions inherit the source's grace window per partition.
- **Doesn't help with the `tap` sub-window pattern.** Two windows
  over the same source's same partition each maintain their own
  deque. The parked `tap` primitive (in PLAN.md) addresses that.

## Where this shows up

- **Batch operator** — [Reshape → partitionBy](/docs/series/reshape#partitionby)
  has the operator-level reference.
- **Live operator** — `LivePartitionedSeries` and the chainable
  `LivePartitionedView` are documented under
  [Live transforms](/docs/live/live-transforms).
- **Triggers** — synchronised partitioned rolling builds on clock
  triggers. See [Triggers](./triggers).
- **Series** — `partitionBy` works uniformly on both
  `TimeSeries<S>` and `LiveSeries<S>`. See [Series](./series).
