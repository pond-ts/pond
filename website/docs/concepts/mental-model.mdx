# Mental model

Hold this one picture and the rest of pond follows, in TypeScript, Rust
or Python alike.

A **series** is a schema-typed, ordered collection of events. **Events** carry a
key plus a typed payload. **Operators** transform series into series; **reducers**
compress events into values.

<MentalModel />

Every operator returns a series whose columns are known: their names and
kinds (number, text, true/false, …) follow from the input and the
operator. That single rule is what makes the algebra **closed**: you keep
chaining, and a bucket _is_ just a smaller series (same API, no second
primitive to learn).

How the column list is checked depends on the language. In TypeScript
the compiler tracks it, so reading a column that isn't there fails before
the code runs. In Rust and Python it is checked when the code runs, as
polars does: asking for a missing column, or treating text as numbers,
is an error that names the column and lists the ones there are.

## The three series types

The key's _kind_ picks the type, and the type decides which operators exist:

| Type              | Keyed by                      | Carries                                           |
| ----------------- | ----------------------------- | ------------------------------------------------- |
| **`TimeSeries`**  | a temporal key (batch)        | the full algebra incl. calendar/clock operators   |
| **`LiveSeries`**  | a temporal key (streaming)    | the same operator surface, incremental cost model |
| **`ValueSeries`** | a monotonic **non-time** axis | the ordering-based operators only — no calendar   |

All three exist in every language under the same names. `TimeSeries` and
`LiveSeries` are **peers**, not layers: same schema type, same
operators, different cost models (whole-collection vs. incremental).
[`ValueSeries`](/docs/series/value-series) drops in when the natural x of your data is a
_quantity_ (distance, work) rather than the wall clock.

The vocabulary each operator assumes — temporal keys, sequences, windowing,
triggers, partitioning, late data, the value axis — is defined page by page in
**[Concepts](/docs/concepts/)**. Read those reference-style once the picture above is
clear.

## Coming from pandas?

`pandas`'s `.resample()` covers both directions; pond splits them. The
names are the same in every language, in each language's own spelling
(`group_by` in Rust and Python, `groupBy` in TypeScript):

- **Downsample** (fewer rows out than in) — `aggregate` ≈ `.resample().agg()`
- **Upsample / regrid** (one row per grid point, hold or interpolate) — `align` ≈ `.asfreq()` + `.ffill()` / `.interpolate('time')`
- `rolling` ≈ `.rolling().agg()`
- `within` / `overlapping` / `trim` ≈ `.loc[]` slicing with three explicit meanings
- `reduce` ≈ `.agg()` on the whole frame
- `group_by` / `groupBy` ≈ `.groupby(col)`

In Python a series is built from, and turned back into, a pandas, polars
or pyarrow frame (`pond.TimeSeries(df)`, `series.to_pandas()`), so pond
can sit in the middle of pandas code. See [Python](/docs/python/).

See [Aggregation](/docs/series/aggregation) for the deep dive on bucketing.

## Coming from pondjs?

| pondjs                   | pond-ts                                                |
| ------------------------ | ------------------------------------------------------ |
| `TimeSeries` (sorted)    | `TimeSeries` (1:1 conceptually; methods differ)        |
| `Collection` (unordered) | `TimeSeries` — pond-ts only exposes the sorted variant |
| `IndexedEvent`           | `Event<Interval>`                                      |
| `TimeRangeEvent`         | `Event<TimeRange>`                                     |
| `Pipeline` + processors  | method chain on `TimeSeries`                           |
| `Pond` / `Aggregator`    | batch `aggregate()` or `LiveAggregation`               |

pond-ts deliberately drops the `Collection` / `TimeSeries` distinction: a bucket
_is_ a smaller `TimeSeries`, so anything that works on a series works on a bucket
— same API, no second primitive.
