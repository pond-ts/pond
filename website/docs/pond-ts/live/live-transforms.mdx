# Live Transforms

Live transforms build incremental processing pipelines on top of
[`LiveSeries`](./live-series). Events flow through a chain of views and
accumulators, each subscribing to its upstream source and emitting
results to downstream consumers. Everything is synchronous and driven
by data — no background timers, no implicit scheduling.

The same vocabulary as batch
[`TimeSeries`](../../pond-ts/concepts/series): `filter`, `map`,
`select`, `window`, `aggregate`, `rolling`, `diff`, `rate`,
`pctChange`, `fill`, `cumulative`, `sample`. Each method exists in
two flavors — batch over an immutable snapshot, live over an incoming
stream — with the same shape of output. If you learned the vocabulary
in [Transforms](../transforms/aggregation), most of this page will
read as "the same thing, but incremental."

## LiveView: filter, map, select, window

`LiveView` wraps any live source with a per-event transform. The built-in
methods on `LiveSeries` return pre-configured views. `filter` also takes an
[expression](../transforms/expressions#live-filter) such as
`col('cpu').gt(0.5)` in place of the function:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
import { LiveSeries, Sequence } from 'pond-ts';

const live = new LiveSeries({
  name: 'metrics',
  schema: [
    { name: 'time', kind: 'time' },
    { name: 'cpu', kind: 'number' },
    { name: 'mem', kind: 'number' },
    { name: 'host', kind: 'string' },
  ] as const,
});

// Filter: only events from one host
const api1 = live.filter((e) => e.get('host') === 'api-1');

// Map: transform values. `e.get('cpu')` narrows to `number | undefined`
// from the schema; pass the event through unchanged when the value is
// missing, otherwise write the transformed number back.
const pct = live.map((e) => {
  const cpu = e.get('cpu');
  return cpu === undefined ? e : e.set('cpu', cpu * 100);
});

// Select: narrow the schema to specific columns. An unknown column name
// (or an array instead of spread names) throws when select() is called.
const cpuOnly = live.select('cpu');

// Window: bounded view over recent data
const last5m = live.window('5m'); // time-based
const last100 = live.window(100); // count-based
```

</TabItem>

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{ColumnDef, ColumnKind};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("mem", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;

    // Filter: only events from one host.
    let api1 = live.filter(live.root(), |e| {
        e.string("host").ok().flatten() == Some("api-1")
    })?;

    // Map: new values for each event, one cell per value column in schema
    // order. A gap stays a gap.
    let pct = live.map(live.root(), |e| {
        let cpu = e.number("cpu").ok().flatten();
        vec![
            cpu.map(|c| (c * 100.0).into()),
            e.value("mem").unwrap().cloned(),
            e.value("host").unwrap().cloned(),
        ]
    })?;

    // Select: only the named columns. An unknown name is an error.
    let cpu_only = live.select(live.root(), &["cpu"])?;
    assert!(live.select(live.root(), &["nope"]).is_err());

    // Window: the last 30 seconds, or the last 2 events.
    let last_30s = live.window(live.root(), "30s")?;
    let last_two = live.window_rows(live.root(), 2)?;

    for (t, cpu, mem, host) in [
        (0, 0.2, 50.0, "api-1"),
        (20_000, 0.4, 55.0, "api-2"),
        (40_000, 0.6, 52.0, "api-1"),
        (60_000, 0.8, 60.0, "api-2"),
        (70_000, 1.0, 58.0, "api-1"),
    ] {
        live.push(t, [Some(cpu.into()), Some(mem.into()), Some(host.into())])?;
    }

    assert_eq!(live[api1].len(), 3);
    assert_eq!(live[pct].last().unwrap().number("cpu")?, Some(100.0));
    let names: Vec<&str> = live[cpu_only]
        .schema()
        .iter()
        .map(|c| c.name.as_str())
        .collect();
    assert_eq!(names, ["time", "cpu"]);
    let times: Vec<i64> = live[last_30s].events().map(|e| e.begin()).collect();
    assert_eq!(times, [40_000, 60_000, 70_000]);
    assert_eq!(live[last_two].len(), 2);
    Ok(())
}
```

A count window is `window_rows`. `map` returns one cell per value column and cannot change an event's time.

</TabItem>
</Tabs>

Under `ordering: 'reorder'`, `window()` eviction is not re-applied
when a late event is inserted — a late event can temporarily sit
"outside" the declared window until the next prune. See
[Late-event scope](#late-event-scope) for the full picture.

Views maintain their own event buffer and implement the `LiveSource` interface,
so they compose by stacking:

```ts
// Snapshot the windowed view into a TimeSeries for batch analytics

```

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{ColumnDef, ColumnKind};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("mem", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    // Each view is the source of the next.
    let api1 = live.filter(live.root(), |e| {
        e.string("host").ok().flatten() == Some("api-1")
    })?;
    let cpu = live.select(api1, &["cpu"])?;
    let pipeline = live.window(cpu, "1m")?;

    for (t, cpu, mem, host) in [
        (0, 0.2, 50.0, "api-1"),
        (20_000, 0.4, 55.0, "api-2"),
        (40_000, 0.6, 52.0, "api-1"),
        (60_000, 0.8, 60.0, "api-2"),
        (70_000, 1.0, 58.0, "api-1"),
    ] {
        live.push(t, [Some(cpu.into()), Some(mem.into()), Some(host.into())])?;
    }

    // A copy of the windowed view, as a batch series.
    let ts = live[pipeline].to_time_series()?;
    assert_eq!(ts.column("cpu")?.numbers()?.get(0), Some(0.6));
    assert_eq!(ts.len(), 2); // api-1 within a minute of 70 s
    Ok(())
}
```

```rust
use pond_rs::live::{LiveSeries, Output, OutputKind};
use pond_rs::{ColumnDef, ColumnKind};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let api1 = live.filter(live.root(), |e| {
        e.string("host").ok().flatten() == Some("api-1")
    })?;
    live.watch(api1, OutputKind::Event)?;

    let out = live.push(0, [Some(0.2.into()), Some("api-1".into())])?;
    let [Output::Event { event, .. }] = &out[..] else {
        panic!()
    };
    assert_eq!(event.number("cpu")?, Some(0.2));
    // Filtered out: nothing comes back.
    assert!(
        live.push(1_000, [Some(0.4.into()), Some("api-2".into())])?
            .is_empty()
    );

    // Stop getting them.
    live.unwatch(api1, OutputKind::Event)?;
    assert!(
        live.push(2_000, [Some(0.6.into()), Some("api-1".into())])?
            .is_empty()
    );
    Ok(())
}
```

pond-rs has no listeners. `watch` the view, and each push returns its events.

</Tabs>

### Cleanup

Call `dispose()` to unsubscribe a view from its source and stop receiving events.

## LiveAggregation: bucketed aggregation

`LiveAggregation` incrementally aggregates events into time buckets: fixed-size
(`Sequence.every`) or calendar ones (`Sequence.calendar`). Buckets finalize as
the data advances past their boundary.

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const agg = live.aggregate(Sequence.every('1m'), {
  cpu: 'avg',
  mem: 'max',
});

// closed() returns only finalized buckets
const closed = agg.closed();

// snapshot() includes the current open bucket's partial value
const snap = agg.snapshot();
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("mem", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let agg = live.aggregate(
        live.root(),
        &Sequence::every("1m")?,
        &[Agg::of("cpu", Reducer::Avg), Agg::of("mem", Reducer::Max)],
    )?;
    // Built on a view: only api-1's events.
    let api1 = live.filter(live.root(), |e| {
        e.string("host").ok().flatten() == Some("api-1")
    })?;
    let api1_agg = live.aggregate(
        api1,
        &Sequence::every("1m")?,
        &[Agg::of("cpu", Reducer::Avg)],
    )?;

    for (t, cpu, mem, host) in [
        (0, 0.2, 50.0, "api-1"),
        (20_000, 0.4, 55.0, "api-2"),
        (40_000, 0.6, 52.0, "api-1"),
        (60_000, 0.8, 60.0, "api-2"),
        (70_000, 1.0, 58.0, "api-1"),
    ] {
        live.push(t, [Some(cpu.into()), Some(mem.into()), Some(host.into())])?;
    }

    // closed(): only finished buckets. The first minute closed at 60 s.
    let closed = live[agg].closed()?;
    assert_eq!(closed.len(), 1);
    assert_eq!(
        closed.column("cpu")?.numbers()?.get(0),
        Some(0.4000000000000001)
    );
    assert_eq!(closed.column("mem")?.numbers()?.get(0), Some(55.0));

    // snapshot(): the open minute too, as it stands.
    let snap = live[agg].snapshot()?;
    assert_eq!(snap.len(), 2);
    assert_eq!(snap.column("cpu")?.numbers()?.get(1), Some(0.9));

    assert_eq!(live[api1_agg].at(0).unwrap().number("cpu")?, Some(0.4));
    Ok(())
}
```

</Tabs>

```rust
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),

        live.root(),
        &Sequence::calendar("day", "America/New_York")?,
        &[Agg::of("cpu", Reducer::Avg)],

    let hour = 3_600_000;

    live.push(mar10 + 16 * hour, [Some(0.4.into())])?; // noon on the 10th, New York
    live.push(mar10 + 30 * hour, [Some(0.6.into())])?; // the 11th

    // New York's clocks moved forward on the 10th: a 23-hour day.
    let day = live[daily].at(0).unwrap();
    assert_eq!(day.begin(), mar10 + 5 * hour);
    assert_eq!(day.end() - day.begin(), 23 * hour);
    assert_eq!(day.number("cpu")?, Some(0.4));
    Ok(())
}
```

### Reading the current value

This is a common first stumble: `LiveAggregation` implements
`LiveSource<S>`, so `.length` and `.at(index)` are available — but they
expose **only closed buckets**. The in-progress bucket is _not_ reachable
through index-style access. Reach for `.at(0)` / `.at(agg.length - 1)`
right after a few pushes and you'll get `undefined` until the first
bucket closes.

For the current partial value you have three paths, from lightest to
heaviest:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
// 1. 'bucket' event — fires on every contributing push with the
//    provisional bucket. Zero allocation on the happy path.
agg.on('bucket', (event) => {
  renderLiveValue(event.get('cpu'));
});

// 2. snapshot() — returns a TimeSeries that includes the open bucket
//    as its last row. Good for "render on a tick" dashboards.
const snap = agg.snapshot();
const currentCpu = snap.last()?.get('cpu');

// 3. Snapshot the source and run batch aggregate. Every bucket in
//    `{ range }` is populated immediately, no waiting for closure.
const batch = live
  .toTimeSeries()
  .aggregate(Sequence.every('1m'), { cpu: 'avg' }, { range });
const currentCpu = batch.last()?.get('cpu');
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, Output, OutputKind};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let minute = Sequence::every("1m")?;
    let avg = [Agg::of("cpu", Reducer::Avg)];
    let agg = live.aggregate(live.root(), &minute, &avg)?;
    // 1. Bucket outputs: the open bucket as it stands, after every event.
    live.watch(agg, OutputKind::Bucket)?;

    let mut current = Vec::new();
    for (t, cpu) in [
        (0, 0.2),
        (20_000, 0.4),
        (40_000, 0.6),
        (60_000, 0.8),
        (70_000, 1.0),
    ] {
        for out in live.push(t, [Some(cpu.into()), Some("api-1".into())])? {
            if let Output::Bucket { event, .. } = out {
                current.push((event.begin(), event.number("cpu")?));
            }
        }
    }
    assert_eq!(current.last(), Some(&(60_000, Some(0.9))));

    // len() and at() see closed buckets only.
    assert_eq!(live[agg].len(), 1);

    // 2. snapshot(): the open bucket is the last row.
    let snap = live[agg].snapshot()?;
    assert_eq!(snap.last().unwrap().number("cpu")?, Some(0.9));

    // 3. A batch aggregate over a copy of the series.
    let batch = live.to_time_series()?.aggregate(&minute, &avg)?;
    assert_eq!(batch.last().unwrap().number("cpu")?, Some(0.9));
    Ok(())
}
```

pond-rs's batch `aggregate` has no `range` option: its buckets run from the first event to the last.

</TabItem>
</Tabs>

**When to use which**:

| Need                                                         | Use                                                |
| ------------------------------------------------------------ | -------------------------------------------------- |
| Alert / export / store **finalized** minute totals           | `agg.on('event', ...)` or `agg.closed()`           |
| Live UI that tracks the **current** bucket as it grows       | `agg.on('bucket', ...)` or `agg.snapshot()`        |
| Dashboard render with a **uniform grid** incl. empty buckets | `live.toTimeSeries().aggregate(seq, m, { range })` |
| Cheap one-shot read of the current partial value             | `agg.snapshot().last()`                            |

The batch path (`live.toTimeSeries().aggregate(...)`) re-validates events
on each call, so it's not free — but for typical dashboard cadences
(seconds to tens of seconds) the cost is negligible, and you get batch
semantics for free: every bucket in the range appears, the partial
trailing bucket included. If the reducer you want is array-producing
(`unique`, `top(n)`) and you need a uniform grid of per-minute values
with an `undefined` / empty bucket on quiet minutes, the batch path is
the right call — live `LiveAggregation` only materializes buckets when
an event lands in them.

#### `tail + reduce` for "current state" without bucketing

Sometimes you don't want a bucketed time series at all — you want a
single record summarizing the source's current or recent state. `tail`
gives you a trailing slice; `reduce` collapses a series to one record:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
// "Current" — whole series, one record
const state = live.toTimeSeries().reduce({
  cpu: 'avg',
  host: 'unique',
});
// => { cpu: number | undefined;
//      host: ReadonlyArray<ScalarValue> | undefined }

// "Recent" — trailing 30s, one record
const recent = live.toTimeSeries().tail('30s').reduce({
  cpu: 'p95',
  host: 'top3',
});
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Scalar};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    for (t, cpu, host) in [
        (0, 0.2, "api-1"),
        (20_000, 0.4, "api-2"),
        (40_000, 0.6, "api-1"),
        (60_000, 0.8, "api-2"),
        (70_000, 1.0, "api-1"),
    ] {
        live.push(t, [Some(cpu.into()), Some(host.into())])?;
    }
    let hosts = [Scalar::from("api-1"), Scalar::from("api-2")];

    // "Current": the whole series, one record.
    let state = live.to_time_series()?.reduce(&[
        Agg::of("cpu", Reducer::Avg),
        Agg::of("host", Reducer::Unique),
    ])?;
    assert_eq!(state.number("cpu")?, Some(0.6));
    assert_eq!(state.array("host")?, Some(&hosts[..]));

    // "Recent": the trailing 30 seconds, one record.
    let recent = live.to_time_series()?.tail("30s")?.reduce(&[
        Agg::of("cpu", Reducer::Percentile(95.0)),
        Agg::of("host", Reducer::Top(3)),
    ])?;
    assert_eq!(recent.number("cpu")?, Some(0.99));
    assert_eq!(recent.array("host")?, Some(&hosts[..]));
    Ok(())
}
```

`reduce` returns a `Reduced`, read by output name with `number`, `array` and so on.

</TabItem>
</Tabs>

Fields narrow per-entry from the reducer name _and_ from the source
column's declared kind: numeric reducers (`'sum'`, `'avg'`, `'count'`,
`'median'`, `'stdev'`, `'difference'`, any `p${number}`) yield
`number | undefined`; `'unique'` and any `top${number}` yield
`ReadonlyArray<T> | undefined` where `T` matches the source column
(`ReadonlyArray<string>` for `kind: 'string'`, etc.); `'first'` /
`'last'` / `'keep'` preserve the source column kind. No `as`-casts
needed at the call site.

`tail(duration)` is the temporal counterpart to `Array.slice(-n)`: it
keeps events whose `begin()` is strictly greater than
`lastEvent.begin() - duration`. Called with no argument it's the
identity (whole series), and it composes with every other `TimeSeries`
method, not just `reduce` — plot the last 30s, aggregate just the last
hour, etc.

Use this shape for stat cards, alert decisions, and the top-of-dashboard
"right now" readout — anywhere a bucketed grid would be overkill.

#### In React: `useCurrent`

For React consumers, `@pond-ts/react` packages the
`subscribe + tail + reduce` dance into a single hook. Full reference:
[`useCurrent`](../../react/hooks#usecurrent). The short version:

```tsx
import { useCurrent } from '@pond-ts/react';

function StatCards({ live }) {
  const { cpu, host } = useCurrent(live, {
    cpu: 'avg',
    host: 'unique',
  });
  // cpu:  number | undefined
  // host: ReadonlyArray<string | number | boolean> | undefined

  const recent = useCurrent(
    live,
    { cpu: 'p95' },
    { tail: '30s', throttle: 200 },
  );

  return (
    <>
      <Stat label="CPU (all)" value={cpu} />
      <Stat label="CPU p95 (30s)" value={recent.cpu} />
      <Stat label="Hosts seen" value={host?.join(', ') ?? '—'} />
    </>
  );
}
```

React hooks are TypeScript only. In Rust, `live.reduce(from, &aggs)` keeps a
record like this up to date as events arrive (see
[Live series → Rolling windows and reduce](../../pond-rs/live#rolling-windows-and-reduce)).

`useCurrent` returns a stable-shape record even when the source is
empty (every mapped field is `undefined`), so destructuring on first
render is safe. Types narrow per-entry: `'avg'` yields `number`,
`'unique'` yields `ReadonlyArray<ScalarValue>`, `` `top${number}` ``
yields an array, other reducers fall back to the source column kind.

**Reference stability** (v0.5.6+): the returned record and each of
its fields are reference-stable across renders as long as the
underlying value is structurally unchanged. A new event push that
leaves `host: 'unique'` with the same elements keeps
`current.host` pointing at the same array, so
`useMemo([current.host], …)` and `useEffect([current.host], …)`
only re-run when the set actually changes. Per-field — if `cpu`
shifts but `host` doesn't, `current.cpu` is a new number (as it
should be) while `current.host` stays stable.

### Subscriptions

<Tabs groupId="language" queryString>

```ts
// Fires when a bucket finalizes
agg.on('event', (event) => {
```

<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, Output, OutputKind};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let agg = live.aggregate(
        live.root(),
        &Sequence::every("1m")?,
        &[Agg::of("cpu", Reducer::Avg)],
    )?;
    live.watch(agg, OutputKind::Event)?; // a bucket closed
    live.watch(agg, OutputKind::Bucket)?; // the open bucket, as it stands
    live.watch(agg, OutputKind::Update)?; // every source event

    let describe = |out: Vec<Output>| -> Vec<String> {
        out.into_iter()
            .map(|o| match o {
                Output::Event { event, .. } => format!(
                    "event [{} – {}] {:?}",
                    event.begin(),
                    event.end(),
                    event.number("cpu").unwrap()
                ),
                Output::Bucket { event, .. } => {
                    format!(
                        "bucket {} {:?}",
                        event.begin(),
                        event.number("cpu").unwrap()
                    )
                }
                Output::Update { .. } => "update".into(),
                _ => unreachable!(),
            })
            .collect()
    };

        [
            "bucket 60000 Some(0.8)",
            "event [0 – 60000] Some(0.6)",
            "update"
        ]
    );
    Ok(())
}
```

### Grace period for out-of-order events

In messaging systems, events often arrive slightly out of order. The `grace`
option delays bucket closing so late events can still accumulate into their
correct bucket:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const live = new LiveSeries({
  name: 'metrics',
  schema,
  ordering: 'reorder',
  graceWindow: '10s',
});

// Grace defaults from the source's graceWindow — no need to repeat it
const agg = live.aggregate(Sequence.every('1m'), { cpu: 'avg' });

// Or override with an explicit value. `live.aggregate` takes no options,
// so build the aggregation directly to pass one.
const agg2 = new LiveAggregation(
  live,
  Sequence.every('1m'),
  { cpu: 'avg' },
  { grace: '5s' },
);
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveOptions, LiveSeries, OrderingMode};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::with_options(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),

            .ordering(OrderingMode::Reorder)
            .grace_window("10s"),

    // Takes the series' 10-second grace.
    let agg = live.aggregate(live.root(), &minute, &avg)?;

    let agg2 = live.aggregate_with(live.root(), &minute, &avg, Some("5s"))?;

    live.push(62_000, [Some(0.7.into())])?;
    live.push(58_000, [Some(0.9.into())])?; // late, both still open
    live.push(66_000, [Some(0.1.into())])?; // 5 s past the minute: agg2 closes
    assert_eq!((live[agg].len(), live[agg2].len()), (0, 1));
    live.push(59_000, [Some(0.3.into())])?; // late: only agg takes it
    live.push(71_000, [Some(0.2.into())])?; // 10 s past: agg closes

    assert_eq!(
        live[agg].at(0).unwrap().number("cpu")?,

    Ok(())
```

In pond-rs the override is `aggregate_with(from, &sequence, &aggs, Some("5s"))`.

</TabItem>
</Tabs>

When the source is a `LiveSeries` with a `graceWindow`, `LiveAggregation`
inherits that value as its default grace period. You can still override it with
an explicit `grace` option. If the source has no grace window (e.g. strict
ordering), the default is zero — buckets close immediately.

With a grace period active, a bucket doesn't finalize until the data's watermark
(highest timestamp seen) advances past `bucket.end + grace`. During that window:

- Late events route to their correct bucket and update the partial aggregate
- The `bucket` event fires with each update, reflecting the revised state
- `snapshot()` includes all pending buckets as provisional results

Once the grace window expires, the bucket closes normally and fires the `event`
event with the final value. Events arriving after their bucket's grace window
has expired are silently dropped.

**Tip:** pair `ordering: 'reorder'` on the source `LiveSeries` with a
`graceWindow` — the aggregation will automatically inherit the same tolerance
for late events.

### Late-event scope \{#late-event-scope\}

`graceWindow` works at exactly two boundaries in the live pipeline:

- **`LiveSeries` ingest** — rejects events older than
  `latest − graceWindow` under `ordering: 'reorder'`. Guarantees the
  buffer's temporal extent covers any event it accepts.
- **`LiveAggregation` bucket closure** — buckets stay open until the
  watermark passes `bucket.end + grace`, so late events within the
  grace window land in the correct bucket.

**That's it.** Downstream live transforms **do not** re-flow late
events through historical state:

- `LiveRollingAggregation` treats a late insertion as a new output
  event at its insertion point. It does _not_ re-scan historical
  windows to include the late event in their totals.
- `LiveView.window()` doesn't re-apply eviction when an event is
  reordered in — a late event can temporarily sit "outside the
  window" until the next prune.
- Subscribers' `'event'` callback fires identically for on-time and
  reordered insertions; there is no "this was late" payload.
- React hooks (`@pond-ts/react`) inherit the above.

If you need late-event correctness propagated through every operator
— a late event at t=T triggering recomputation of every window and
aggregation that covers t=T — pond-ts is not the right tool. Reach
for a streaming engine with watermarks, triggers, and retraction. See
Akidau's
[Streaming 102](https://www.oreilly.com/radar/the-world-beyond-batch-streaming-102/)
for what full late-event propagation looks like in that class of
system.

For the common "moderate reorder at ingest, bucketed aggregation for
dashboards" case, the two supported boundaries are sufficient — and
the retention guard (`graceWindow ≤ retention.maxAge`) is enforced
at construction to prevent the accept-then-evict race.

## LiveRollingAggregation: sliding-window reduction

`LiveRollingAggregation` maintains a sliding-window aggregate that updates on every source
event. It supports time-based and count-based windows:

:::note[Heads up on late events]
Under `ordering: 'reorder'`, a late event becomes a new output event
at its insertion point — this method does **not** re-scan historical
windows to include it. See
[Late-event scope](#late-event-scope) for the full story and the set
of guarantees that hold at each point in the pipeline.
:::

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const rolling = live.rolling('5m', { cpu: 'avg' });

// Current aggregate value
rolling.value(); // { cpu: 0.42 }

// Updates on every source event
rolling.on('update', (val) => {
  console.log('rolling avg:', val.cpu);
});
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, Output, OutputKind};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],

    let rolling = live.rolling(live.root(), "2s", &[Agg::of("cpu", Reducer::Avg)])?;
    live.watch(rolling, OutputKind::Update)?;

                updates.push(v[0].clone());
```

### As a LiveSource

`LiveRollingAggregation` also satisfies `LiveSource`. Each source event produces an output
event containing the rolling aggregate at that point, preserving the source
event's timestamp:

```ts
const rolling = live.rolling('5m', { cpu: 'avg' });

// Output buffer grows with each source event
rolling.length; // number of output events so far
rolling.at(0); // first output event (aggregate after first source event)
rolling.at(-1); // most recent output event

// Push-based notification
rolling.on('event', (event) => {
  // event.begin() is the source event's timestamp
  // event.get('cpu') is the rolling average at that point
});
```

This makes `LiveRollingAggregation` the live equivalent of the batch `rolling()` method. The
output buffer grows unboundedly — downstream consumers can compose with
`window()` to bound it if needed.

### Trigger-based emission

A rolling aggregation's emission cadence is controlled by an
optional `trigger` on the `rolling` call:

```ts
import { Trigger } from 'pond-ts';

const rolling = timings.rolling(
  '1m',
  { latency: 'p95' },
  { trigger: Trigger.every('30s') },
);
```

Three triggers are available — `Trigger.event()` (default, per
source event), `Trigger.every(duration)` /
`Trigger.clock(sequence)` (per epoch-aligned boundary), and
`Trigger.count(n)` (per N events). Synchronised partitioned
rolling builds on clock triggers — every known partition emits
together at each boundary tick.

For the full reference (parameters, emission semantics, trigger ×
partition matrix, sync-rolling restrictions), see
[Triggering](./triggering).

## Multi-window rolling: many windows, one ingest \{#multi-window\}

When the use case wants **several trailing windows over the same
source** (e.g. a 1-minute baseline of `avg`/`stdev` plus a 200-ms
current-tick window of raw samples for anomaly detection), pass a
keyed record of mappings to `live.rolling`:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
import { LiveSeries, Trigger } from 'pond-ts';

const live = new LiveSeries({ name: 'cpu', schema });

const fused = live.rolling(
  {
    '1m': {
      cpu_avg: { from: 'cpu', using: 'avg' },
      cpu_sd: { from: 'cpu', using: 'stdev' },
    },
    '200ms': { cpu_samples: { from: 'cpu', using: 'samples' } },
  },
  { trigger: Trigger.every('200ms') },
);

fused.on('event', (event) => {
  // All four columns from both windows on a single event.
  const samples = event.get('cpu_samples') as ReadonlyArray<number>;
  const z = samples.map(
    (s) => (s - event.get('cpu_avg')) / event.get('cpu_sd'),
  );
  // anomaly density, threshold counting, etc.
});
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, RollingOptions, RollingWindow, Trigger};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Scalar};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "cpu",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
        ],
    )?;
    let fused = live.rolling_windows(
        live.root(),
        &[
            RollingWindow::new(
                "1m",
                &[
                    Agg::new("cpu_avg", "cpu", Reducer::Avg),
                    Agg::new("cpu_sd", "cpu", Reducer::Stdev),
                ],
            ),
            RollingWindow::new("200ms", &[Agg::new("cpu_samples", "cpu", Reducer::Samples)]),
        ],
        &RollingOptions::new().trigger(Trigger::every("200ms")?),
    )?;

        (0, 1.0),
        (100, 3.0),
        (150, 5.0),
        (250, 7.0),
        (300, 9.0),
        (420, 2.0),

        .schema()
        .iter()
        .map(|c| c.name.as_str())
        .collect();
    assert_eq!(names, ["time", "cpu_avg", "cpu_sd", "cpu_samples"]);
    let e = live[fused].at(0).unwrap();
    assert_eq!(e.begin(), 200);
    let (avg, sd) = (e.number("cpu_avg")?.unwrap(), e.number("cpu_sd")?.unwrap());
    assert_eq!((avg, sd), (4.0, 2.23606797749979));
    let samples = e.array("cpu_samples")?.unwrap();
    assert_eq!(
        samples,
        [Scalar::from(3.0), Scalar::from(5.0), Scalar::from(7.0)]
    );

    // A score per sample, as in the TypeScript.
    let z: Vec<f64> = samples
        .iter()
        .map(|s| match s {
            Scalar::Number(x) => (x - avg) / sd,
            _ => f64::NAN,
        })
        .collect();
    assert_eq!(z.len(), 3);

    // The same output name in two windows is refused.
    let twice = [
        RollingWindow::new("1m", &[Agg::new("x", "cpu", Reducer::Avg)]),
        RollingWindow::new("5s", &[Agg::new("x", "cpu", Reducer::Max)]),
    ];
    assert!(
        live.rolling_windows(live.root(), &twice, &RollingOptions::new())
            .is_err()
    );
    Ok(())
}
```

`rolling_windows` takes a list of `RollingWindow`s, one per window.

</TabItem>
</Tabs>

Conceptually equivalent to declaring two `live.rolling(...)` calls
over the same source plus a per-`(ts, key)` join — but **one ingest
pass** updates all windows' reducer state, **one merged event** is
emitted per trigger fire, and the consumer code is one event handler.

### Properties

- **Single trigger across all windows by design.** Per-window
  cadence is rare; users who need it fall back to two separate
  `rolling()` calls (paying the per-event pipeline cost twice).
- **Time-based windows only.** Object keys are duration strings
  (`'1m'`, `'200ms'`, `'5s'`); count-based windows
  (`live.rolling(100, ...)`) stay on the single-window form.
- **Duplicate output column names** across windows are rejected at
  construction. Each column name appears once in the merged
  schema.
- **Single-window equivalence.** `live.rolling('1m', m, opts)` and
  `live.rolling({ '1m': m }, opts)` produce identical output.

### As a LiveSource

Like `LiveRollingAggregation`, multi-window rolling implements the
`LiveSource<Out>` contract — `length`, `at(i)`, `on('event', fn)`,
`dispose()`. Output buffer grows unbounded; compose with
`.window(duration)` for a bounded read-side view.

### Performance characteristics

The architectural win is that per-event pipeline overhead
(`#routeEvent`, `_pushTrustedEvents`, `ingest`) runs once
regardless of N windows; only per-window reducer-state updates
remain O(N) — and separate rollings pay that same cost. At N=5
windows over 100k events × 100 hosts, multi-window is **2.4×
faster** and uses **34% of the heap** of N separate rollings. See
[Rolling → Performance](../transforms/rolling#multi-window) for
the full bench table.

For the conceptual framing alongside the other windowing modes,
see [Windowing](../../pond-ts/concepts/windowing#multi-window-rolling-live).

## Per-event transforms: diff, rate, pctChange

These methods compute per-event deltas by comparing consecutive events. Each
returns a `LiveView` that tracks the previous event's values in a closure.

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
// Absolute difference between consecutive events
const deltas = live.diff('requests');

// Per-second rate of change (delta / time gap in seconds)
const perSec = live.rate('requests');

// Percentage change: (curr - prev) / prev
const pctChg = live.pctChange('requests');
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{LiveSeries, LiveView, Node};
use pond_rs::{ColumnDef, ColumnKind, Fill, FirstRow};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "web",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("requests", ColumnKind::Number),
        ],
    )?;
    // The change since the previous event.
    let deltas = live.diff(live.root(), &["requests"])?;
    // That change per second.
    let per_sec = live.rate(live.root(), &["requests"])?;
    // As a fraction of the previous value.
    let pct_chg = live.pct_change(live.root(), &["requests"])?;
    // Without the first event...
    let dropped = live.diff_with(live.root(), &["requests"], FirstRow::Drop)?;
    // ...or with its gap filled with 0.
    let diffs = live.diff(live.root(), &["requests"])?;
    let zeroed = live.fill(diffs, &[("requests", Fill::Zero)])?;

    for (t, requests) in [(0, 100.0), (2_000, 150.0), (4_000, 120.0)] {
        live.push(t, [Some(requests.into())])?;

        live[node]
            .events()
            .map(|e| e.number("requests").unwrap())
            .collect()
    };
    assert_eq!(col(deltas), [None, Some(50.0), Some(-30.0)]);
    assert_eq!(col(per_sec), [None, Some(25.0), Some(-15.0)]);
    assert_eq!(col(pct_chg), [None, Some(0.5), Some(-0.2)]);
```

## Carry-forward transforms: fill, cumulative

### fill

Replaces `undefined` values as events arrive. Only forward-looking strategies
are supported in live mode — `bfill` and `linear` require future values and
will throw.

<TabItem value="ts" label="TypeScript" default>

```ts
// Carry forward the last known value for all columns

// Fill undefined with zero

// Per-column strategies and literal fill values
const mixed = live.fill({ cpu: 'hold', host: 'unknown' });

// Cap consecutive fills
```

```rust
use pond_rs::{ColumnDef, ColumnKind, Fill, Value};

    let mut live = LiveSeries::new(
        "metrics",

            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
```

## Sampling: bounded-memory thinning \{#sampling\}

`sample({ stride: N })` thins the event stream going to downstream consumers
without affecting this `LiveSeries`'s own `length`, `at(i)`, listeners, or
`stats()` counters. The headline use case: **decouple downstream baseline
window length from event rate**.

Streaming aggregator memory scales as
`O(window_seconds × event_rate × per_partition_count)`. At firehose rates
(70k events/s × 80 partitions), a 1-minute rolling baseline holds ≈4M events;
a 5-minute baseline at the same rate is the kind of number where you'd
hit Node's heap ceiling. Stride-thinning the input stream means a longer
baseline for the same memory budget — and `sd / sqrt(N)` standard error
typically still drops far below per-event noise even at stride 10.

Returns a `LiveView<S>`, so the chainable surface (`filter`, `rolling`,
`reduce`, `select`, `map`, `diff`, `rate`, `cumulative`, `fill`, …) is
immediately available downstream of the sample.

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
// Canonical shape: per-host stride before per-host rolling.
const baselines = live
  .partitionBy('host')
  .sample({ stride: 10 })
  .rolling('5m', { cpu_avg: 'avg', cpu_sd: 'stdev' });

baselines.on('event', (e) => {
  // 1-in-10 of each host's stream feeds a 5-minute rolling window.
});
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{CollectOptions, LiveSeries, PartitionOptions};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sample};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let hosts = live.partition_by(live.root(), "host", &PartitionOptions::new())?;
    // Every 2nd event of each host, then a 1-minute count per host.
    let counts = live.apply(
        hosts,
        |live, host| {
            let sampled = live.sample(host, Sample::Stride(2))?;
            Ok(live
                .rolling(sampled, "1m", &[Agg::new("events", "cpu", Reducer::Count)])?
                .id())
        },
        &CollectOptions::new(),
    )?;

    for i in 0..8 {
        let host = if i % 2 == 1 { "b" } else { "a" };
        live.push(i * 1_000, [Some((i as f64).into()), Some(host.into())])?;
    }

    // The counts are of the sampled events: times 2 for the true count.
    let rows: Vec<_> = live[counts]
        .events()
        .map(|e| (e.begin(), e.number("events").unwrap()))
        .collect();
    assert_eq!(
        rows,
        [
            (2_000, Some(1.0)),
            (3_000, Some(1.0)),
            (6_000, Some(2.0)),
            (7_000, Some(2.0))
        ]
    );
    // The series itself still counts every event.
    assert_eq!(live.stats().ingested, 8);
    Ok(())
}
```

In pond-rs, `sample` goes inside the per-host chain (`apply` or `per_partition`), so each host gets its own stride counter. This program also shows the counts after sampling, from the section below.

### Multi-entity series — see `partitionBy` \{#sampling-multi-entity\}

A pre-partition `live.sample({ stride: N })` applied to a structured
input stream (events arriving in round-robin host order) silently keeps
the same subset of partitions and drops the rest. A stride-10 filter on
a 80-host round-robin stream keeps 8 of 80 hosts; the other 72 vanish
from downstream rollings without warning.

The fix is the canonical shape above: **chain `sample` after
`partitionBy`**. Each partition gets its own stride counter, so every
host's stream is thinned independently.

This is the same multi-entity consideration that applies to every
stateful live operator (`rolling`, `aggregate`, `fill`, `diff`, `rate`,
`cumulative`, `pctChange`, `reduce`) — see
[Cleaning data → Multi-entity series](../transforms/cleaning#multi-entity-series--see-partitionby)
for the broader pattern. Sample follows the same convention.

### Reducer counts after sampling

Reducers downstream of `sample` (`'count'`, `'sum'`, `topN`) reflect the
**sampled stream**, not the source. Multiply count-shaped outputs by the
stride to estimate true counts:

```ts
const sampled = live.partitionBy('host').sample({ stride: 10 });
const counts = sampled.rolling('1m', {
  events: { from: 'cpu', using: 'count' },
});
// counts.value().events × 10 ≈ true count over the 1m window
```

`live.stats().ingested` and `live.on('batch', cb)` are **upstream** of any
`.sample(...)` op — they continue counting true throughput. Only consumers
downstream of `sample` see the thinned stream.

### Reservoir sampling on the live side

Not in v0.17.0. Random K-of-N (Algorithm R) replacement on a live source
emits non-prefix evictions, which the current eviction-mirroring protocol
(`'evict'` event + cutoff-based prune) doesn't handle. It's queued for a
later release once the streaming RFC's `LiveChange` exact-removal channel
lands.

Reservoir sampling on the **snapshot side** is unconstrained and ships
in v0.17.0 — see
[Sampling → Reservoir (random K-of-N)](../transforms/sampling#reservoir).
For the firehose visualization shape (`series.sample({ reservoir }).toRows()`),
materialize the live buffer first via `live.toTimeSeries()`.

### EMA smoothing via map

Exponential moving average doesn't need a dedicated class — it's a stateful
closure inside `map()`:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
function ema(alpha: number) {
  let prev: number | undefined;
  return live.map((event) => {
    const raw = event.get('cpu'); // number | undefined from schema
    if (raw === undefined) return event; // pass through; no new prev
    prev = prev === undefined ? raw : alpha * raw + (1 - alpha) * prev;
    return event.set('cpu', prev);
  });
}

const smoothed = ema(0.3);
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{ColumnDef, ColumnKind, Value};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let alpha = 0.3;
    let mut prev: Option<f64> = None;
    // The closure keeps its own state between events.
    let smoothed = live.map(live.root(), move |e| {
        let host = e.value("host").unwrap().cloned();
        let Some(raw) = e.number("cpu").unwrap() else {
            return vec![None, host]; // pass through; no new prev
        };
        let next = prev.map_or(raw, |p| alpha * raw + (1.0 - alpha) * p);
        prev = Some(next);
        vec![Some(next.into()), host]
    })?;

    for (t, cpu) in [
        (0, Some(1.0)),
        (1_000, Some(2.0)),
        (2_000, None),
        (3_000, Some(4.0)),
    ] {
        live.push(t, [cpu.map(Value::from), Some("a".into())])?;
    }
    let cpu: Vec<_> = live[smoothed]
        .events()
        .map(|e| e.number("cpu").unwrap())
        .collect();
    assert_eq!(cpu, [Some(1.0), Some(1.2999999999999998), None, Some(2.11)]);
    Ok(())
}
```

### Partitioned rolling → one unified series \{#collect\}

`partitionBy(col)` runs a per-partition pipeline; `collect()` fans the
per-partition outputs back into a single `LiveSeries` you can snapshot,
`window()`, or hand to a React hook:

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

```ts
const baseline = live
  .partitionBy('host')
  .rolling('1m', {
    host: { from: 'host', using: 'last' }, // partition tag drops by default — carry it
    avg: { from: 'cpu', using: 'avg' },
    sd: { from: 'cpu', using: 'stdev' },
  })
  .collect({ retention: { maxAge: '30m' } });
// LiveSeries<{ time, host, avg, sd }> — one series, every host interleaved
```

</TabItem>
<TabItem value="rust" label="Rust">

```rust
use pond_rs::live::{CollectOptions, LiveSeries, PartitionOptions};
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),
            ColumnDef::optional("host", ColumnKind::String),
        ],
    )?;
    let hosts = live.partition_by(live.root(), "host", &PartitionOptions::new())?;
    let baseline = live.apply(
        hosts,
        |live, host| {
            let rolling = live.rolling(
                host,
                "1m",
                &[
                    // The host column is not carried over unless you keep it.
                    Agg::new("host", "host", Reducer::Last),
                    Agg::new("avg", "cpu", Reducer::Avg),
                    Agg::new("sd", "cpu", Reducer::Stdev),
                ],
            )?;
            Ok(rolling.id())
        },
        // The gathered series keeps its own retention; set it here.
        &CollectOptions::new().max_age("30m"),
    )?;

    for (t, cpu, host) in [
        (0, 1.0, "a"),
        (1_000, 3.0, "b"),
        (2_000, 3.0, "a"),
        (3_000, 5.0, "b"),
    ] {
        live.push(t, [Some(cpu.into()), Some(host.into())])?;
    }

    // One series, every host interleaved.
    let names: Vec<&str> = live[baseline]
        .schema()
        .iter()
        .map(|c| c.name.as_str())
        .collect();
    assert_eq!(names, ["time", "host", "avg", "sd"]);
    let rows: Vec<_> = live[baseline]
        .events()
        .map(|e| {
            let host = e.string("host").unwrap().unwrap().to_string();
            (
                e.begin(),
                host,
                e.number("avg").unwrap(),
                e.number("sd").unwrap(),
            )
        })
        .collect();
    let row = |t, h: &str, a, s| (t, h.to_string(), Some(a), Some(s));
    assert_eq!(
        rows,
        [
            row(0, "a", 1.0, 0.0),
            row(1_000, "b", 3.0, 0.0),
            row(2_000, "a", 2.0, 1.0),
            row(3_000, "b", 4.0, 1.0)
        ]
    );
    Ok(())
}
```

As in pond-ts, the gathered series keeps everything unless `CollectOptions` sets a retention, and the host column comes through only if a reducer carries it.

</TabItem>
</Tabs>

Two things to know about `collect()`:

- It is an **append-only fan-in** — it subscribes to every partition
  (current and future) and pushes their output events into the unified
  buffer. Per-partition retention bounds each partition; the unified
  buffer's retention is **independent and does not inherit**. Pass
  `{ retention: … }` to bound it, or it grows unbounded.
- On the per-event (non-`clock`) partitioned `rolling`, the partition
  column **drops** unless you carry it through with a passthrough
  reducer (`host: { from: 'host', using: 'last' }`). The synced
  `Trigger.clock(...)` and fused forms auto-inject it instead.

This composition is the basis of an incremental dashboard baseline that
costs a gather per render instead of a full re-walk — see
[Recipe: Incremental ±σ baselines](../../recipes/streaming-baseline)
for the end-to-end pattern (≈16× at dashboard scale).

```rust
use pond_rs::live::LiveSeries;
use pond_rs::{Agg, ColumnDef, ColumnKind, Reducer, Sequence};

fn main() -> Result<(), pond_rs::PondError> {
    let mut live = LiveSeries::new(
        "metrics",
        vec![
            ColumnDef::required("time", ColumnKind::Time),
            ColumnDef::optional("cpu", ColumnKind::Number),

    let agg = live.aggregate(
        live.root(),
        &Sequence::every("1m")?,
        &[Agg::of("cpu", Reducer::Avg)],

    live.remove(agg)?;
    live.remove(rolling)?;
    live.remove(view)?;
    // A removed handle gives an error; the series carries on.
    assert!(live.get(rolling).is_err());
    live.push(60_000, [Some(0.7.into())])?;
    assert_eq!(live.len(), 2);
    Ok(())
}
```

After `remove`, `live.get(node)` gives an error, so a removed node can no longer be read. pond-ts keeps a disposed object readable.
