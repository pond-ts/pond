# Creating series

## Introduction

Everything in pond starts with getting data **in**. Which door you use is
decided by the shape the data arrives in — not by what you plan to do with it
afterwards. Every batch door produces the same `TimeSeries`, with the same
schema contract and the same operator surface; the live door builds a
`LiveSeries` that snapshots to one on demand.

| Your data arrives as…                                   | Door                         | Section                                         |
| ------------------------------------------------------- | ---------------------------- | ----------------------------------------------- |
| Row tuples you built in code                            | `new TimeSeries({ rows })`   | [The constructor](#the-constructor)             |
| A JSON payload — rows of arrays or objects              | `TimeSeries.fromJSON`        | [`fromJSON`](#fromjson)                         |
| Struct-of-arrays JSON — `{ time: [...], close: [...] }` | `TimeSeries.fromColumns`     | [JSON columnar](#json-columnar)                 |
| Typed arrays off a binary decoder                       | `TimeSeries.fromColumns`     | [Float64Array columnar](#float64array-columnar) |
| A decoded Apache Arrow `Table`                          | `TimeSeries.fromArrow`       | [Arrow](#arrow)                                 |
| Events arriving one at a time, forever                  | `new LiveSeries(…)` + `push` | [Live data](#live-data)                         |
| Rows keyed by a value, not a time                       | `ValueSeries.fromColumns`    | [ValueSeries](./value-series)                   |

Going the other way: `toJSON` serializes for the wire, `toRows` / `toObjects`
hand back in-memory rows, and `toArrow` hands the raw column buffers to another
columnar engine.

Two smaller doors round out the set: `TimeSeries.fromEvents(events, { schema })`
for `Event` objects you already hold, and
`TimeSeries.fromPoints(points, { schema })` for wide `{ ts, … }` objects (the
shape charts hand back).

### The constructor

```ts
import { TimeSeries } from 'pond-ts';

const schema = [
  { name: 'time', kind: 'time' },
  { name: 'cpu', kind: 'number' },
  { name: 'host', kind: 'string' },
] as const;

const cpu = new TimeSeries({
  name: 'cpu',
  schema,
  rows: [
    [Date.parse('2025-01-01T00:00:00Z'), 0.31, 'api-1'],
    [Date.parse('2025-01-01T00:01:00Z'), 0.44, 'api-1'],
  ],
});
```

The `as const` on the schema is load-bearing — without it, TypeScript widens the
schema tuple to a regular array and the column kinds widen to `string`, breaking
type inference across every transform.

Rows must be in **non-decreasing key order** — the constructor throws on
out-of-order rows, and the error names the offending row. For unsorted input (a
CSV read in arrival order, merged sources), pass `sort: true` to sort on
construction instead of pre-sorting yourself:

```ts
const cpu = new TimeSeries({ name: 'cpu', schema, rows, sort: true });
```

The sort is **stable**, so rows with equal keys keep their input order. Every
other ingest door takes the same `sort` option and means the same thing by it.

For the full schema-as-contract story (kinds, narrowing, `required: false`), see
[Concepts → Series](./concepts/series). For messy or partially-bad input, see
[Cleaning data](../pond-ts/transforms/cleaning).

### Live data

When events arrive incrementally rather than as a finished dataset, construct a
`LiveSeries` with the same schema and push into it:

```ts
import { LiveSeries } from 'pond-ts';

const live = new LiveSeries({
  name: 'cpu',
  schema, // same schema as batch
  retention: { maxEvents: 10_000 }, // bounded buffer
  ordering: 'reorder', // accept moderately late events
  graceWindow: '5s', // ... up to 5s late
});

live.push([Date.now(), 0.42, 'api-1']);
live.pushMany([
  [Date.now() + 1, 0.43, 'api-1'],
  [Date.now() + 2, 0.45, 'api-2'],
]);
```

`live.toTimeSeries()` snapshots to an immutable batch series at any time — the
snapshot is independent of future pushes, and `live.toJSON()` is shorthand for
snapshotting and serializing. Retention and ordering details are on
[Late data](./concepts/late-data); the reference page is
[LiveSeries](../pond-ts/live/live-series).

The rest of this page is about batch ingest, and applies to a `LiveSeries` only
through that snapshot.

### Coming from pandas

`TimeSeries.fromJSON` ≈ `pd.read_json(…, convert_dates=True, date_format='iso')`;
`toJSON` ≈ `.to_json(orient='records'|'values', date_format='iso')`;
`parse.timeZone` ≈ `.tz_localize(…)` on a naive `DatetimeIndex`;
`TimeSeries.fromColumns` ≈ `pd.DataFrame({...})` over aligned arrays;
`fromArrow` / `toArrow` ≈ `pa.Table` interop.

## JSON

JSON is the row-shaped door — the natural fit for a REST endpoint, and the right
default. Both `TimeSeries` and `LiveSeries` round-trip through it via `toJSON` /
`fromJSON`, and the shape is identical for both: consumers of the JSON don't need
to know which side it came from.

A JSON-serialized `TimeSeries` is just three fields — the series name, the schema
(the same tuple you'd pass to the constructor), and the rows:

```json
{
  "name": "cpu",
  "schema": [
    { "name": "time", "kind": "time" },
    { "name": "cpu", "kind": "number" },
    { "name": "host", "kind": "string" }
  ],
  "rows": [
    [1735689600000, 0.31, "api-1"],
    [1735689660000, 0.44, "api-1"]
  ]
}
```

By default rows are arrays — one per event, positional by schema column. The
alternative is object rows keyed by column name (see [`toJSON`](#tojson)).

The temporal key column always comes first. Its serialized form depends on its
kind:

| Kind          | JSON shape                                                         |
| ------------- | ------------------------------------------------------------------ |
| `'time'`      | `number` (ms since epoch) or ISO string (`"2025-01-01T00:00:00Z"`) |
| `'timerange'` | `[startMs, endMs]` or `{ start, end }`                             |
| `'interval'`  | `[label, startMs, endMs]` or `{ value, start, end }`               |

Everything else is the obvious thing — numbers become numbers, strings become
strings, arrays become arrays, `undefined` is serialized as `null` (and parsed
back to `undefined` on ingest).

:::note[Coming from pondjs?]
pondjs serialized `TimeRangeEvent` as a nested shape — `[[startMs, endMs], data]`
— with the temporal key wrapped inside the event payload. pond-ts flattens: the
timerange key is the first positional element (or the `timerange` key on an
object row), and payload columns follow. A legacy pondjs JSON payload needs a
small remap before it round-trips through `TimeSeries.fromJSON`.
:::

### `fromJSON`

Pass the parsed JSON, get back a typed `TimeSeries`:

```ts
import { TimeSeries } from 'pond-ts';

const schema = [
  { name: 'time', kind: 'time' },
  { name: 'cpu', kind: 'number' },
  { name: 'host', kind: 'string' },
] as const;

const cpu = TimeSeries.fromJSON({
  name: 'cpu',
  schema,
  rows: [
    [1735689600000, 0.31, 'api-1'],
    [1735689660000, 0.44, 'api-1'],
  ],
});
```

In React, when the server emits a full pond-ts payload, the client is one line:

```ts
const payload = await (await fetch('/api/cpu')).json();
const cpu = TimeSeries.fromJSON(payload);
```

When the server emits just the rows, supply the schema on the client:

```ts
const rows = await (await fetch('/api/cpu/rows')).json();
const cpu = TimeSeries.fromJSON({ name: 'cpu', schema, rows });
```

Rows must be in non-decreasing key order, same as the constructor; pass
`sort: true` for a payload that isn't guaranteed ordered.

#### Timestamp inputs

`fromJSON` accepts two timestamp formats per event key, and they can mix freely:

- **Number** — milliseconds since the Unix epoch, UTC. No ambiguity.
- **ISO string** — parsed by the same rules as `Date.parse`. If the string
  carries an offset (`Z`, `+02:00`), the offset is used as-is. If it doesn't (a
  **wall-clock string** like `'2025-01-01T09:00'`), you must supply
  `parse.timeZone` or the library doesn't know what wall you mean.

#### Wall-clock strings: `parse.timeZone`

The common case for analytics data: timestamps were emitted in local time and
never carried a zone offset.

```ts
const ts = TimeSeries.fromJSON({
  name: 'cpu',
  schema,
  rows: [
    // "2025-01-01 at 09:00 Madrid local" → 08:00:00 UTC.
    ['2025-01-01T09:00', 0.42, 'api-1'],
    ['2025-01-01T10:00', 0.51, 'api-1'],
  ],
  parse: { timeZone: 'Europe/Madrid' },
});

ts.at(0)!.begin();
// 1735714800000 — i.e. 2025-01-01T08:00:00Z
```

Does your input need it?

| Input shape                   | Example                    | `parse.timeZone`?                  |
| ----------------------------- | -------------------------- | ---------------------------------- |
| Number (ms since epoch)       | `1735689600000`            | Ignored — UTC by definition.       |
| String with offset (`Z`)      | `'2025-01-01T09:00Z'`      | Ignored — offset is authoritative. |
| String with offset (`±hh:mm`) | `'2025-01-01T09:00+01:00'` | Ignored — offset is authoritative. |
| Wall-clock string (no offset) | `'2025-01-01T09:00'`       | **Required.** Throws without it.   |

If your upstream source is a spreadsheet, a log scraper, or a database export
without a zone column, you're almost certainly in the wall-clock row — pass
`parse.timeZone` once per `fromJSON` call.

#### Object rows

If your JSON source uses keyed objects instead of positional arrays, `fromJSON`
accepts that shape too:

```ts
const ts = TimeSeries.fromJSON({
  name: 'windows',
  schema: [
    { name: 'interval', kind: 'interval' },
    { name: 'value', kind: 'number' },
    { name: 'active', kind: 'boolean' },
  ] as const,
  rows: [
    {
      interval: { value: 'a', start: '2025-01-01', end: '2025-01-02' },
      value: 1,
      active: true,
    },
  ],
  parse: { timeZone: 'UTC' },
});
```

Object rows and array rows can't mix within a single `rows` array. The library
picks the format based on the first row.

#### Missing values

`null` in a cell becomes `undefined` on the event; a column marked
`required: false` in the schema accepts both `null` and a missing key (in object
rows):

```ts
const schema = [
  { name: 'time', kind: 'time' },
  { name: 'cpu', kind: 'number' },
  { name: 'status', kind: 'string', required: false },
] as const;

TimeSeries.fromJSON({
  name: 'cpu',
  schema,
  rows: [
    ['2025-01-01T00:00Z', 0.42, 'ok'],
    ['2025-01-01T00:01Z', 0.51, null], // status is undefined
  ],
});
```

Columns without `required: false` reject `null` at validation time — if a cell is
sometimes-present, make it optional in the schema.

Note that `fromJSON` **rejects** a non-finite provided number (`NaN`, `Infinity`)
outright rather than treating it as a gap. The columnar doors are looser here;
see [Common ingest issues](#non-finite-numbers-mean-different-things-per-door).

### `toJSON`

Serializes back to the JSON-friendly shape.

```ts
const payload = series.toJSON();
// { name, schema, rows: [[ts, v, ...], ...] }

JSON.stringify(payload);
// One string; round-trips via TimeSeries.fromJSON(JSON.parse(...)).
```

#### Array vs object rows

Default is array rows (smaller on the wire, faster to parse). Request object rows
when readability matters more than size:

```ts
const compact = series.toJSON();
// rows: [[1735689600000, 0.31, "api-1"], ...]

const keyed = series.toJSON({ rowFormat: 'object' });
// rows: [{ time: 1735689600000, cpu: 0.31, host: "api-1" }, ...]
```

Both formats round-trip through `fromJSON` with the same output.

#### Round-trip fidelity

`series.toJSON()` → `JSON.stringify` → `JSON.parse` → `TimeSeries.fromJSON(…)`
preserves:

- Series `name`
- Every column name + kind
- Every row value, including `undefined` (as `null` on the wire)
- Event order
- Key objects (`Time` / `TimeRange` / `Interval`) with exact timestamps

It does **not** preserve:

- Schema `required: true | false` flags that differ from validation defaults —
  declare them explicitly on both sides if you need that narrowing to survive.
- Comments, whitespace, or any non-payload metadata you might be tempted to
  attach.

If the two ends of a round-trip share the same `schema` tuple (as `const`),
TypeScript's type-narrowing on `.get()` is preserved through the round-trip at
the type level. If one end imports a different schema, the narrowing is only as
good as what both ends import.

#### In-memory exports

When the consumer is in-process rather than across a wire, skip the JSON shape
entirely. `toRows` / `toObjects` preserve `Time` / `TimeRange` / `Interval` as
objects instead of flattening them to numbers and tuples:

```ts
const rows = series.toRows();
// ReadonlyArray of [key, ...values] tuples with *object* keys

const objects = series.toObjects();
// ReadonlyArray of { [colName]: value } objects with *object* keys
```

Both are faster than `toJSON` (no JSON-shape conversion) and are the right choice
for tests, other library code, and React components. They do **not** round-trip
via `fromJSON` — use `toJSON` for wire-format serialization.

## Columnar

`fromJSON` takes row tuples, but plenty of sources hand you data
**struct-of-arrays** already: a bulk columnar JSON payload, a protobuf message
with `repeated double` fields, an Arrow record batch. Reshaping those back into
rows just to hand them to `fromJSON` costs a transpose pass you don't need — and
throws away the fact that pond's own storage is columnar underneath, so a
columnar input can often be adopted rather than copied.

Three variants, same underlying ingest engine:

| Input                                         | Door          | Cost                                     |
| --------------------------------------------- | ------------- | ---------------------------------------- |
| `{ time: number[], close: number[] }`         | `fromColumns` | One copy per column                      |
| `{ time: Float64Array, close: Float64Array }` | `fromColumns` | **Zero-copy** — buffers adopted          |
| A decoded Apache Arrow `Table`                | `fromArrow`   | **Zero-copy** for single-chunk `Float64` |

All three share the same rules for missing values, ordering, and `sort` — see
[Missing values and ordering](#missing-values-and-ordering).

**Supported kinds.** The columnar doors build a `time`-keyed series with
`number` and `string` value columns. Other key kinds (`interval`, `timerange`)
and other value kinds (`boolean`, arrays) throw for now — the row doors take
those.

:::info[Value-keyed data has its own door]
`fromColumns` builds a **time**-keyed series. If your rows are keyed by a
monotonic _value_ instead — an options chain keyed by strike, a spectrum keyed by
frequency — don't launder the axis through a fake `time` column:
**`ValueSeries.fromColumns({ name, schema, columns, sort })`** is the same door
with a `'value'`-kind axis column in place of time. Same inputs, same zero-copy
adoption, same `sort: true`. Data that _starts_ time-keyed projects into
value-land with [`byValue`](./concepts/value-axis) instead.
:::

### JSON columnar

The plain-array case — exactly what `JSON.parse` gives you for a columnar wire
payload, with no transpose needed:

```ts
import { TimeSeries } from 'pond-ts';

const schema = [
  { name: 'time', kind: 'time' },
  { name: 'open', kind: 'number' },
  { name: 'close', kind: 'number' },
  { name: 'venue', kind: 'string' },
] as const;

const bars = TimeSeries.fromColumns({
  name: 'AAPL',
  schema,
  columns: {
    time: [1735689600000, 1735689660000, 1735689720000],
    open: [193.1, 193.4, 193.2],
    close: [193.4, 193.2, 193.6],
    venue: ['XNAS', 'XNAS', 'XNAS'],
  },
});
```

Each entry in `columns` is one column's values, aligned by index; every column
must be the same length as the key column, and a missing or mismatched column
throws naming itself. String columns are dictionary-encoded when that pays off,
which is why a low-cardinality column like `venue` above costs almost nothing.

Plain arrays are always **copied** into pond's storage — the source array is
yours to keep mutating afterwards.

#### Missing values and ordering

A `null`/`undefined` cell, or a non-finite numeric cell (`NaN`, `Infinity`), is a
**gap**:

```ts
TimeSeries.fromColumns({
  name: 'AAPL',
  schema,
  columns: {
    time: [1735689600000, 1735689660000],
    open: [193.1, 193.4],
    close: [193.4, null], // gap
    venue: ['XNAS', null], // gap
  },
});
```

The rule is identical across every columnar input shape — plain array, typed
array, Arrow. It is deliberately looser than `fromJSON`, which rejects a
non-finite _provided_ number outright.

Columns must be in **non-decreasing key order**, same invariant as `fromJSON` — an
out-of-order key throws, naming the offending index. Pass `sort: true` to sort
rows by key before construction; the sort is stable, like `fromJSON`'s. Sorting
**disables zero-copy adoption** on every door below: a reorder needs fresh
buffers.

### Float64Array columnar

A numeric column can be a `Float64Array` instead of a plain array — the shape a
binary decoder (protobuf packed doubles, a fixed-point decoder after descaling)
hands back directly:

```ts
const bars = TimeSeries.fromColumns({
  name: 'AAPL',
  schema,
  columns: {
    time: Float64Array.from([1735689600000, 1735689660000, 1735689720000]),
    open: Float64Array.from([193.1, 193.4, 193.2]),
    close: Float64Array.from([193.4, 193.2, 193.6]),
  },
});
```

This is the fast path: a `Float64Array` column is **adopted directly**, not
copied — no re-materialization, no per-row intake. It's also why `fromColumns` is
one function taking either shape rather than two separate ones: a plain-array
caller and a typed-array caller want the same ingest, just with a different
(adopt vs. copy) cost underneath, so the wire format changes only your _decoder_.

String columns have no typed-array form — hand them a `string[]`. Passing a typed
array for a `'string'`-kind column throws rather than stringifying numbers.

:::warning[Adopted, not copied]
Because a `Float64Array` column is adopted by reference, mutating the source
buffer after construction mutates the series. Hand `fromColumns` a buffer you're
done writing to — freshly decoded output is the common case and is naturally
safe. `number[]` columns are always copied, so this only applies to the
typed-array path.
:::

:::tip[Why this matters for interactive charts]
The real cost this solves isn't raw parse speed — it's _when_ the parse happens.
Decoding a hefty series (hundreds of thousands of points) synchronously on the
main thread can stall an animating or panning chart for a visible frame. Because
`fromColumns` accepts `Float64Array`s directly, a decoder can run in a **Web
Worker** and `postMessage` the resulting typed arrays back as **transferable
objects** (zero-copy) — `fromColumns` then adopts them on the main thread for a
fraction of a millisecond per column, instead of a multi-frame freeze. A plain
`number[]` can't transfer this way (it structured-clones), so this pattern
specifically wants the columnar + typed-array path.
:::

### Arrow

pond does **not** depend on `apache-arrow`. You bring your own Arrow, decode the
table however you like, and hand the `Table` over — the input is duck-typed
against the small structural surface pond actually reads (`ArrowTableLike`,
`ArrowVectorLike`, … all exported if you need to satisfy it from something that
isn't arrow-js).

#### `fromArrow`

```ts
import { tableFromIPC } from 'apache-arrow';
import { TimeSeries } from 'pond-ts';

const table = tableFromIPC(
  await (await fetch('/api/bars.arrow')).arrayBuffer(),
);

const bars = TimeSeries.fromArrow(table, { name: 'AAPL', time: 'ts' });
```

The schema is derived from the Arrow fields, so you don't declare one. (You may
supply `S` as `fromArrow<MySchema>(…)` for downstream typing — pond takes that on
trust and does not verify the fields match, exactly as `fromEvents` trusts its
schema.)

| Option     | Default                              | Meaning                                                                                      |
| ---------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| `name`     | `'arrow'`                            | Series name.                                                                                 |
| `time`     | the field named `'time'`             | Which column is the time key. Throws if absent.                                              |
| `timeUnit` | read from the Arrow `Timestamp` type | `'second' \| 'millisecond' \| 'microsecond' \| 'nanosecond'`. An explicit value always wins. |
| `columns`  | every non-time field                 | Value columns to include, in order.                                                          |
| `sort`     | `false`                              | Sort by time key first (disables adoption).                                                  |

**Column handling.** The time key accepts `Timestamp`, `Date32`/`Date64`, and
plain int/float columns, all normalized to epoch ms: a `Timestamp`'s raw-unit
int64 is scaled by its `TimeUnit`, a `Date32`/`Date64` already arrives as epoch-ms
from Arrow's `toArray()` and passes through, and a plain number is taken as ms. A
null in the time key throws. Value columns may be numeric (`Float32` and int
columns convert to `Float64`; nulls become gaps) or `Utf8` strings (dict-encoded;
nulls become gaps). Any other Arrow type — list, struct — throws, naming it; use
`columns` to select a supported subset out of a mixed table.

**What's zero-copy.** Every **single-chunk** `Float64` column's backing
`Float64Array` is adopted as-is, and the time key is converted **BigInt-free** —
Arrow's idiomatic int64 timestamps are recombined from their two int32 halves
rather than `Number(bigint)` per row, measured ~11× faster on the time column
(0.6 ms vs 6.8 ms at 500k rows; `packages/core/scripts/perf-from-arrow.mjs`). A
table decoded from a **multi-record-batch** IPC stream has multi-chunk columns,
whose `toArray()` concatenates into a fresh buffer — still correct, but a copy
rather than an adopt, and the aliasing warning above doesn't apply to it.

#### `toArrow`

The counterpart, and the only export door that isn't row-shaped. pond's columnar
substrate is already laid out the way Arrow wants: the validity bitmap is
LSB-first, one bit per value, 1 = valid; numeric columns are a contiguous
`Float64Array`; booleans a packed bitmap; dict-encoded strings `Int32Array`
indices plus a dictionary. So `toArrow` hands back the buffers pond is already
holding — nothing is copied, reshaped, or re-encoded.

It returns `{ length, fields }` rather than an Arrow `Table`, for the same reason
`fromArrow` takes a duck-typed one: adding a dependency to hand data _out_ would
be a strange price for interop. The caller assembles per field, narrowing on
`type` first:

```ts
import { makeData, makeVector, Float64 } from 'apache-arrow';

const { fields } = series.toArrow();
const f = fields.find((x) => x.name === 'close')!;
if (f.type !== 'float64' && f.type !== 'timestamp') throw new Error(f.type);

const vec = makeVector(
  makeData({
    type: new Float64(),
    length: f.length,
    nullCount: f.nullCount,
    nullBitmap: f.nullBitmap,
    data: f.values, // narrowed to Float64Array by the guard above
  }),
);
```

From there a consumer can reach whatever engine they like — polars, DuckDB,
arrow-js — for work pond doesn't do well, without pond depending on any of it and
without paying a re-ingest to get there.

`toArrow` exports `number`, `string` and `boolean` value columns (a wider set
than ingest accepts); anything else throws, naming the column. Pass
`{ columns: [...] }` to select a subset — the key field(s) are always included.
A `timeRange` or `interval` key becomes two flat fields, `<key>` and
`<key>End`, since Arrow has no interval-of-time type; interval labels ride along
as `<key>Label`. A value column that would collide with one of those synthesized
names throws rather than producing a duplicate field name.

Two cases are **not** zero-copy, named here so the cost is visible: a chunked
column is materialized into one buffer first, and a string column pond chose not
to dictionary-encode is handed over as a plain JS array (Arrow `Utf8` wants
offsets into a UTF-8 byte buffer — building those is the consumer's encode).

:::warning[The buffers are live storage]
`toArrow` hands over pond's actual storage, not copies. Writing to one corrupts
the series it came from — a `TimeSeries` is immutable by contract, not by
defensive cloning. This is the same read-only contract `column(name)`,
`keyColumn()` and `toFloat64Array()` already carry, but it's worth restating when
the buffers cross into another library. Copy first
(`new Float64Array(f.values)`) if the consumer mutates in place.
:::

## Common ingest issues

### Wall-clock strings without `parse.timeZone`

```ts
TimeSeries.fromJSON({
  name: 'cpu',
  schema,
  rows: [['2025-01-01T09:00', 0.42]],
  // no parse.timeZone
});
// Throws — ambiguous local string; needs a zone context.
```

Either add `parse.timeZone`, or switch to an offset-qualified string
(`'2025-01-01T09:00Z'`) or a number (`Date.parse('2025-01-01T09:00Z')`).

### Mixed timestamp formats

Mixing number and ISO-string timestamps within one `rows` array is legal at the
type level — both normalize to ms-since-epoch internally — but it's almost always
a symptom of an upstream bug. Two specific risks worth naming:

- **Silent zone drift.** A run of ISO strings marked with `Z` followed by a run of
  bare wall-clock strings produces events that look ordered but are actually
  offset by the local-vs-UTC delta of the wall-clock rows' zone.
- **Numbers are always UTC.** If you mix numbers and wall-clock strings with
  `parse.timeZone`, the numbers don't pick up the zone — they stay UTC while the
  strings get resolved in the specified zone.

Normalize upstream before shipping the payload over the wire.

### Out-of-order keys

Every door requires **non-decreasing** keys and throws otherwise, naming the
offending row or index. This isn't fussiness: bisect-based operators (`crop`,
`atTime`, range queries) depend on the invariant, and a backwards key on a
trusted columnar door is a corruption signal rather than something to silently
accept.

Pass `sort: true` to sort instead of throwing. To flatten a genuine backwards
blip to a plateau — a different, lossy choice — clamp the keys yourself before
ingest; the library won't mutate your data for you.

### Non-finite numbers mean different things per door

| Door                        | `NaN` / `Infinity` in a value column |
| --------------------------- | ------------------------------------ |
| `fromJSON` / constructor    | **Rejected** — throws                |
| `fromColumns` / `fromArrow` | **Treated as a gap** (missing)       |

The columnar doors are the trusted fast path, where a decoder's `NaN` is
overwhelmingly a sentinel for "no reading" rather than a bad value. If you need a
non-finite to be an _error_ in columnar input, check it before ingest.

### Mutating a buffer you handed to `fromColumns`

Adoption is by reference, so this silently rewrites history:

```ts
const closes = Float64Array.from([193.4, 193.2, 193.6]);

const bars = TimeSeries.fromColumns({
  name: 'AAPL',
  schema,
  columns: { time, open, close: closes },
});

closes[0] = 0; // bars now reports 0 for the first close
```

Hand over a buffer you're done writing to, or pass a copy
(`new Float64Array(closes)`). The same applies in reverse to `toArrow`'s output.
`number[]` columns are always copied, so they're never affected.

### Unsupported kinds on the columnar doors

`fromColumns` / `fromArrow` build a `time`-keyed series with `number` and
`string` value columns. An `interval` or `timerange` key, or a `boolean` / array
value column, throws naming the column and its kind. Route those through
`fromJSON` or the constructor, or select a supported subset via `columns`.

### Object-row JSON from non-pond-ts sources

If you're parsing JSON emitted by a non-pond-ts system, object rows may use
different key names than your schema. Map them first:

```ts
const theirRows: Array<{ ts: number; cpu_pct: number }> = externalData;

const ours = theirRows.map((r) => ({
  time: r.ts,
  cpu: r.cpu_pct,
}));

TimeSeries.fromJSON({ name: 'cpu', schema, rows: ours });
```

The library isn't trying to guess remaps.
