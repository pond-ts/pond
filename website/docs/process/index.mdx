# Processing graphs

**Computations as data.** A processing graph is a list of steps (an
average, a band, the latest value) written as plain JSON, run against a
dataset by a long-lived host that remembers what it has already worked
out. It comes in **TypeScript** (`@pond-ts/process`) and **Rust**
(`pond-process`). Both give every step the same id and the same numbers.

<Tabs groupId="language" queryString>
<TabItem value="ts" label="TypeScript" default>

In TypeScript you build the graph fluently, typed end to end by your own
op vocabulary:

```ts
const graph = process(registry, 'ACME_5m');

const close = graph.column('close');
const average = close.sma({ as: 'average', period: 20 });
const bands = average.bands({ as: 'bands', width: 2 });

const result = host.run(
  graph.outputs({
    average: average.columns(), // packed columns, for a chart
    bands: bands.columns(),
    latest: average.last(), // a small fact
  }),
);
```

</TabItem>
<TabItem value="rust" label="Rust">

In Rust you write the request as JSON with `serde_json::json!`: the same
data the TypeScript builder emits. Slots (`average`, `bands`, `latest`)
are your own names for the steps.

```rust
use std::collections::HashMap;
use std::sync::Arc;

use pond_process::{Host, Registry, study_ops};
use pond_rs::{Column, TimeSeries};
use serde_json::json;

fn main() {
    // The vocabulary: the standard folds (`last`, …) and every finance study.
    let mut registry = Registry::standard();
    for def in study_ops() {
        registry.define(def).unwrap();
    }

    // Sixty daily closes.
    let time: Vec<i64> = (0..60).map(|i| i * 86_400_000).collect();
    let close: Vec<f64> = (0..60).map(|i| 100.0 + (i as f64 * 0.3).sin() * 5.0).collect();
    let bars = TimeSeries::new("ACME", time, vec![Column::optional_raw("close", close)]).unwrap();

    let units = HashMap::from([("close".to_string(), "USD".to_string())]);
    let mut host = Host::new(Arc::new(registry), units);
    host.add("ACME", Arc::new(bars));

    let result = host
        .run(&json!({
            "from": "ACME",
            "nodes": {
                "average": { "op": "sma", "params": { "period": 20 }, "in": ["close"] },
                "bands": { "op": "bollinger", "params": { "period": 20 }, "in": ["close"] },
                "latest": { "op": "last", "in": ["average"] }
            },
            "outputs": {
                "average": { "on": "average" }, // columns, for a chart
                "bands": { "on": "bands" },
                "latest": { "on": "latest" }    // a small fact
            }
        }))
        .unwrap();

    // Columns are named by each step's id: the same id TypeScript gives it.
    let columns = result.columns.as_ref().unwrap();
    assert_eq!(columns[0].0, "p1:sma(close;period=20)");
    assert_eq!(columns.len(), 4); // the average, then the three bands

    // The fact: the latest average, with its unit and where it came from.
    let fact = &result.facts[0];
    assert_eq!(fact["name"], "latest");
    assert_eq!(fact["unit"], "USD");
    assert_eq!(fact["at"], "1970-03-01");
}
```

</TabItem>
</Tabs>

The request is **plain JSON**, the same `{ op, params, inputs }` format a
saved view replays and a tool-calling model composes directly from the
registry's description. One format, one resolver, one content-addressed
cache serving a chart's columns and an agent's facts alike. In
TypeScript the fluent API is the developer's front door; in both
languages the data underneath is the contract.

:::info[Experimental]
Both are new and **experimental**: before 1.0, and the API is expected
to move as friction reports land. Pin an exact version.
:::

```sh
npm install @pond-ts/process pond-ts
```

Peer-depends on `pond-ts`; the pond packages release together, so keep
their ranges in step.

```toml
pond-process = { git = "https://github.com/pond-ts/pond" }
```

## What each language has

The Rust crate is a port of the TypeScript package. Every Rust answer is
checked against a file of cases the TypeScript package writes
(`packages/process/test/fixtures/parity.json`), so the two cannot drift
apart without a test failing.

|                                                              | TypeScript                 | Rust                                                           |
| ------------------------------------------------------------ | -------------------------- | -------------------------------------------------------------- |
| Registry: your own ops and folds, param checks, `describe()` | Yes                        | Yes                                                            |
| Slot and nested requests, every error policy, `toWire`       | Yes                        | Yes                                                            |
| Host: datasets, byte budget, async sources, `maxSources`     | Yes                        | Yes                                                            |
| Basic ops, standard and summary folds                        | Yes                        | Yes                                                            |
| Finance studies as steps                                     | Yes                        | Yes, except the session studies (they need a trading calendar) |
| Fluent builder (`process(registry, …)`)                      | Yes                        | No: write the JSON                                             |
| Joins, ranged recompute (`runRange`), the live graph         | Yes                        | Not yet                                                        |
| JSON Schema for a model (`toJsonSchema`)                     | Yes                        | Not yet: `describe()` gives the same facts as plain JSON       |
| Running requests in parallel                                 | A worker pool (`HostPool`) | Threads inside one host (`with_threads`)                       |

Python and the WebAssembly bridge do not have processing graphs yet.

## When _not_ to use this

Chaining is pond's mental model and stays the right default:

```ts
const out = series
  .rolling('5m', { cpu: 'avg' })
  .aggregate(Sequence.every('1h'), { cpu: 'max' });
```

If the pipeline is known when you write the code, chain it and skip this
package. `@pond-ts/process` exists for the case chaining genuinely cannot
express: when **the pipeline itself is data** —

- constructed at runtime from saved configuration;
- reshaped by a user in a node editor;
- composed by a model against a declared vocabulary;
- one expensive intermediate fanned out to several consumers wanting
  different slices;
- persisted, and run again later against refreshed source data.

## The three layers

Every page in this section is about one of three roles, and keeping them
separate is the design:

1. **The [registry](./registry) declares which operations exist.** It is
   simultaneously the compile-time vocabulary that types the fluent API,
   the runtime validator, the metadata behind a picker, and the source of
   a JSON Schema projection a tool-calling model composes against.
2. **The [request](./requests) is plain data describing one graph.**
   Authored [fluently](./authoring) or composed remotely, it lands on the
   same [data model](./plans), whose identity is content-addressed: the
   same question, however spelled, lands on the same node — which is what
   makes the id a cache key, a column name, and a provenance citation at
   once.
3. **The [host](./host) outlives requests.** It binds datasets, resolves
   remote sources, keeps each binding's graph warm, and answers requests
   with columns, facts, lineage, and per-node timings.

## Relationship to the engine underneath

The plan layer sits on a small pull-based dataflow engine — typed ports,
memoized nodes, dirty propagation that stops when values stop changing.
That engine is exported today, and the
[package README](https://github.com/pond-ts/pond/tree/main/packages/process)
documents it, but the RFC's conclusion (tracked as **[PND-PROCSUB]**) is
that the plan layer is the consumer surface and the engine belongs
underneath it. Prefer the plan layer unless you are building something the
plan layer itself cannot express.
