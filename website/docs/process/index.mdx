# @pond-ts/process

**Computations as data.** A plan — `{ op, params, inputs }` specs forming a
DAG — arrives as JSON, resolves against a declared vocabulary, and runs over
a bound `TimeSeries`. One request serves a renderer asking for drawable
columns and an agent asking for small facts, off one shared,
content-addressed cache.

:::caution[Work in progress]
`@pond-ts/process` is not published yet. These pages describe the in-repo
WIP API, which may change before the first release. Work from a pond
monorepo checkout rather than installing from npm.
:::

## When _not_ to use this

Chaining is pond's mental model and stays the right default:

```ts
const out = series
  .rolling('5m', { cpu: 'avg' })
  .aggregate(Sequence.every('1h'), { cpu: 'max' });
```

If the pipeline is known when you write the code, chain it and skip this
package. `@pond-ts/process` exists for the case chaining genuinely cannot
express: when **the pipeline itself is data** —

- constructed at runtime from saved configuration;
- reshaped by a user in a node editor;
- composed by a model against a declared vocabulary;
- one expensive intermediate fanned out to several consumers wanting
  different slices;
- persisted, and run again later against refreshed source data.

## The three layers

Every page in this section is about one of three roles, and keeping them
separate is the design:

1. **The [registry](./registry) declares which operations exist.** It is
   simultaneously the runtime validator, the metadata behind a picker, the
   compile-time vocabulary for fluent authoring, and the source of a JSON
   Schema projection a tool-calling model composes against.
2. **The [plan](./plans) is plain data describing one graph.** Identity is
   content-addressed: the same question, however spelled, lands on the same
   node — which is what makes the id a cache key, a column name, and a
   provenance citation at once.
3. **The [host](./host) outlives requests.** It binds datasets, resolves
   remote sources, keeps each binding's graph warm, and answers
   [requests](./requests) with columns, facts, lineage, and per-node
   timings.

## Relationship to the engine underneath

The plan layer sits on a small pull-based dataflow engine — typed ports,
memoized nodes, dirty propagation that stops when values stop changing.
That engine is exported today, and the
[package README](https://github.com/pond-ts/pond/tree/main/packages/process)
documents it, but the RFC's conclusion (tracked as **[PND-PROCSUB]**) is
that the plan layer is the consumer surface and the engine belongs
underneath it. Prefer the plan layer unless you are building something the
plan layer itself cannot express.
